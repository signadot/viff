What is there today, read rather than remembered.

**Two places hold model credentials, and both are per PROCESS.**

- verse's own, `config.LLMConfig` — `baseURL`, `apiKey`, `virtualKey`, `model`, one block per
  verse. `Available()` is "an API key is configured", and `/status` shows it masked.
- the coderunner's own, `Config.LLM` — `apiKeyEnv` / `virtualKeyEnv`, env var NAMES rather than
  values, "so a config file that is read, copied and committed carries no secret". The runner
  reads them from its own environment and sends them to the task process.

So the unit of credential is the deployment. Every task a runner executes spends the same key,
and every `llm` spawn in a verse spends that verse's. Wanting a second key today means a second
runner deployment.

**Where it bites**

- **Spend has no owner.** `docs/working/work/task-budget.md` opens on a review that worked for
  twenty minutes after reaching its conclusion and ignored an operator telling it to stop. With
  one key behind every task, the only question that can be answered afterwards is what the VERSE
  spent, never which charter, task or person did.
- **No isolation.** One runaway drive spends the whole org's quota, and a rate limit hit by a
  noisy rule is a rate limit hit by everything else.
- **Blast radius.** A leaked key is the deployment's, not one task's.
- **Tier by deployment.** A cheap model for triage and an expensive one for review is two runners
  today, because the key and the model ride together in one config.

**The two constraints that shape it**

1. **Names, not values.** The coderunner already refuses to hold secrets in a file that can be
   copied. A per-task credential must be a NAME the runner resolves in its own environment (or a
   secret-store ref), never a value on a task record — a task record is readable by whoever may
   read it, and `Provenance` already crosses the wire in the clear.
2. **A credential is not authority.** `task.Provenance` says "deliberately NOT authority… a
   runner must not read Principal and confer anything on the strength of it — that is the
   on-behalf-of model docs/roadmap/authority.md rejects by name". Letting a task name a key it
   would not otherwise hold is exactly that model through a side door, so what a spawn may NAME
   has to be decided by the same grants everything else is.

**What it has to decide**

- **Who chooses the credential.** The spawn in the charter; the provider entity the selection
  picks (`provider.<capability>.<id>` already carries `driver`, `frame`, `tools`, `grant` — a
  credential name would sit beside them and be chosen by the same governed selection); or the
  person the task runs for. The provider entity looks right: it is already where "what the doer
  contributes" lives, and selection is already the governed step.
- **What a runner does with a name it does not have.** There is a rule to copy:
  `Config.Environment(name)` refuses an unknown workspace rather than falling back, "the same
  class of mistake as a misspelled runner that runs in-process", and `MissingLLMCreds` refuses at
  startup AND again at the spawn so a task that cannot finish never starts. A credential name
  should refuse identically.
- **Who may spawn a task that names which key.** Naming the expensive key is an act with a cost,
  which is the shape of a permission.
- **Whether the model travels with it.** Today `model` sits in the same block as the key in both
  places. If a credential is named per task, "which model" either rides with it or becomes a
  second name, and picking one is what makes a cheap-triage/expensive-review split one line
  instead of a deployment.
- **What is recorded.** For spend to have an owner the task record has to say which credential it
  ran under — the name, never the secret — which is also what makes `task-budget.md`'s question
  answerable at all.
