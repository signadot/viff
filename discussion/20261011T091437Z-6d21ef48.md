Decided (2026-10-11):

1. **The finisher goes.** The agent decides what leaves, with `push` as its ordinary tool under both drivers (for codex, through `dynamicTools`). An agent that does not push delivers nothing. Then test how well that works and refine.

2. **Provenance rides on the agent's commits.** The brief asks the agent to write the trailers (`Verse-Task`, `Verse-Principal`, `Verse-Environment`, …); the parent checks them against the launch it holds, and where they are missing or wrong, the parent puts the right ones on. The point is that the trailers are visible to the agent and the agent knows the exact SHAs it is delivering.

   One consequence to settle under 2: putting trailers on an existing commit is a rewrite, so the SHA the agent knows is not the SHA that lands. Two ways to keep the agent's knowledge true: (a) refuse the push with the reason, so the agent re-commits with the right trailers and pushes again, its SHAs intact; or (b) amend, push, and return the new SHA as the push's result so the agent reads it. (a) keeps one author and fits "the agent decides"; (b) always lands something. Default to (a) unless told otherwise.

3. **`ask` for codex**: not decided; see the reading below.

Reading of 3, for the record. Today the driver maps codex's own question tool (`request_user_input`, codex's experimental tool, with its `header`, `options`, `isOther`, `isSecret`, blocking or not) onto a verse question to the task's principal. That works, and it is codex's tool: its description and when the model reaches for it are codex's, and it can change or go upstream. The alternative is to offer verse's `ask` through `dynamicTools`, the same tool the `llm` driver has: `question`, `options`, `within`, `default`, `answerers`. Then the model is told, in verse's words, when and how to hand the turn to a person; a question can carry a deadline and a default, and name who may answer; the conversation mode (`--converse`) means the same thing under both drivers; and a charter or a doc describes one `ask`, not two. Codex's own tool would still be mapped when the model uses it. Low stakes either way; it falls out of the `dynamicTools` bridge once that exists, so it can be decided then.
