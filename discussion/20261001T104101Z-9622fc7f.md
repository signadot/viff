**The late-frame guard from 7b6cb09d does not hold even serially, for an answered record.** Found while adding `waitingOn` to frame-posed questions on verse/ask-next (8987ece4). That commit puts it in the same conditional write as `status`, so it is no more exposed than `status`.

Repro: a mirror test on `entitytest.Store` via `docket(t)`, with no load and no concurrency.

```go
ev := task.Frame{Kind: task.EvPending, ID: "t1~d1", Gate: "ship"}
PostFrameQuestion(store, ev, "t1", "", []string{"user:ann@example.com"})
AnswerQuestion(store, ev.ID, task.Choose(task.Proceed, "user:ann@example.com"))
// Get: status=answered
PostFrameQuestion(store, ev, "t1", "", []string{"user:ann@example.com"})
// Get: status=pending, the verdict and ballots still underneath
```

I logged the conditional write (`When: notStatus(answered), notStatus(orphaned)`): it returns `ok=true`, admitted against a record that `Get` reads as `status: answered`. It failed 3 runs out of 3.

A bare record does refuse it. Writing `{id, status: answered}` and then the same conditional write gives `ok=false`, and the record is untouched. So whether the precondition holds depends on the record's shape: the answered one carries `ballots`, `verdict`, `by`, `answeredAt`, `answerers` and `options`. Timing doesn't explain it. The comments here have treated the residual as a lagging view; this repro has no lag.

Not root-caused. The next step is to bisect which field of the answered payload makes `!not {status: answered}` admit the write.
