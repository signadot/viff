Two decisions taken in the doing, which change the plan's first two bullets:

- **A tool is its command, run as a process.** Each call builds the argv of the `verse` command it mirrors and runs this same binary (`os.Executable()`). The plan said a verb's inline request-building would be pulled into a function the tool shares. That cannot work for a long-lived server: the command tree keeps one invocation's flags, filters and principal in package state (`flt`, `trig`, `asOverride`, `lastPrintEmpty`), which every `rootCmd()` resets, and `cli.Run` calls `os.Exit` once a parent has dispatched. The process boundary also makes "tools add no operation" literal, makes concurrent calls safe, and re-reads the config and the login on every call, which covers the deferred credential concern for every tool except `verse_wait`. The one in-process piece is still `verse_wait`'s `askWatch`, as designed.
- **No `--as` on `verse mcp`.** The server acts as whoever `verse` acts as there: the config, the login, `VERSE_USER`. A host that wants another identity sets the environment in its server entry. That is v27eah17's point 2 ("the server takes the identity from the configuration of the person, in the same way as the command line").

Mechanics a later step relies on:

- Every parameter goes on the command line as `--name=value`, so a value starting with `-` stays a value. `TestADataToolValueIsNeverAFlag` checks this.
- A failure is the command's stderr; for a usage error, only the text from `usage error:` on.
- An answer over `mcpAnswerMax` (64 KiB) is refused with how to narrow it. It is never cut.
- The tests build the binary once into TestMain's dir (`builtVerse`) and connect go-sdk's in-memory transports (`mcpSession`, `callTool` in `cmd/verse/mcp_test.go`).
