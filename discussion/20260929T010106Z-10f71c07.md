**Prep for stages 2 and 4** (design notes, no code): `verse/scratchpad/stage2-prep.md` and `verse/scratchpad/stage4-prep.md`, grounded at a28d37f2. The questions they raise for the owner:

**Stage 2, revision and changes**
- **The consent gap is not a re-fire, as the plan said.** While a gate waits, `claimFlight` blocks a second firing (trigger/edge.go:284), and an edit to the subject only moves the deadline. The gap has two parts:
  - The pose is worded at the firing, but the action's bindings are read from the subject as it stands after the yes (trigger.go:534-537, 948; deref.go:514-524).
  - After a restart, the same `gateID` is posed again over the waiting record, and ballots cast for the old words count toward the new ones.
  - Proposed: separate resolving the action from applying it. Keep a digest of what was asked: pose, options, answerers, about, and the resolved action. Ask again only when the digest changes, and on a yes apply what was resolved for the revision that was answered.
- **The registry is where a stale revision must be refused,** since an answer is delivered before the record is written (server.go:3184).
- **Open:** a settled rule gate that fires again within its keep reuses its id, against "an ask settles once". Bump the revision on the same id, or give each new asking its own id?
- **Open:** the field's name (`revision` clashes with the store's revisions), and whether an answer that names no revision is refused.

**Stage 4, resolvers**
- **Q1, a person's resolver and a place's always overlap.** Overlap has to be judged per (ask, party), and an ask to ana about X fits both `{to: ana}` and `{about: X}`. Options:
  - refuse, so the two never coexist;
  - a match names `to` or `about`, not both;
  - a fixed rule: the party's resolver before the place's.
- **Q2, anyone can claim someone else's match first.** If a match is only routing, bob can install `{to: ana}` first, and ana can never install her own. Sources avoid this because the installer must own what it claims (`checkPlace`, versed/place.go:31). Options:
  - first come, first served;
  - the grant to answer for someone declares the match;
  - declaring and granting are one act.
- **The overlap refusal exists for sources** (`verseio.Disjoint`, io/own.go:278). It stays decidable only if a match refuses payload filters and compares `to` as the literal party named, without expanding groups. Today's `resolver.Owner` comment (resolver.go:396) argued a refusal was undecidable.
- **Migration:** nothing in the repo uses a gate or spawn `resolver:`, and no deploy profile installs a resolver, so the old machinery can be deleted rather than migrated.
