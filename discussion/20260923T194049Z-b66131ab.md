Decided: the candidate "verse refuses to spend a credential that is readable by
everyone" is REJECTED, and the answer is documentation rather than a check.

Refusing to read something that is readable by all is counter-intuitive; the docs should rather
read "this is how keys can work with verse today. You must fence, here's how, check the
reference for why. Keys in verse are not cryptographically protected, merely protected by
convention of permissions. If you need encryption, use something else or this mechanism in
combination with an encryption mechanism."

The sharper reason is that the rule fails its own test. "Readable by all ⇒
refuse" has an obvious counter-model: an open dogfood verse, deliberately sharing one cheap
bounded key. Refusing that is verse deciding somebody's risk tolerance, in a place where the
permissions model otherwise reports what a record says and nothing more.

It would also have been theatre with a cost. It blocks a working arrangement while NOT closing
the path that matters — a key fenced to `group:reviewers` is still readable by any rule owned by
anyone in that group — so it stops the easy case, leaves the real one, and teaches "verse protects
my keys", which is false. A property a reader can reason about beats a guarantee that is not one.

## What was written instead

`docs/provider-selection.md`, under the credential section: **What protects a key here, and what
does not.** It states the guarantee in one line — verse keeps a key from people the record
excludes, and keeps nothing from people the record admits — and then the two edges:

- **Fence the place**, once, with both halves: `verse perms acme keys --grants '[]'
  --child-grants '{}'`. Proven: with only `--child-grants '{}'` a stranger still read
  the key, because the place itself still held out `read: *` and a child inherits that. With both,
  a node created afterwards is refused to a stranger — and so is one that was already there, since
  a node with no record of its own inherits the place's.
- **A rule that may read a key may also copy it**, into an io's place, where a connector says it
  out loud. There is no check against this and there is not going to be one: the same read that
  lets a spawn spend the key lets a rule copy it, and refusing the second while allowing the first
  is a distinction the model cannot draw.

And where to go when permissions are not enough: keep the secret in the runtime's environment and
name no credential, or store something verse can hold safely (an encrypted value the runner can
open, a reference into a secret manager) and accept that rotation moves there too.

## What this leaves open

The issue's question is unchanged and still open — whether the store should hold bearer strings at
all, and whether a launch should carry one. What is now closed is only the sub-question of whether
verse should police the perms on a credential node. It should not.
