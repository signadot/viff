ANALYSED, and the first finding is that this is not a gate flake. Gate answering is where it was
first REPORTED, not what it is about. Reproduced deliberately, instrumented, and the mechanism is
now legible end to end.

## Reproducing it

Neither CPU starvation nor parallelism alone does it: eight concurrent `GOMAXPROCS=1 go test
./versed/` runs pass 8/8, and three whole-repo `go test ./...` runs pass clean. What reproduces it
is COMPETING LOAD from other processes — this issue's own first report said as much ("a session
that was also running go test and several local verses"), and it is the part that was never turned
into a recipe:

```sh
for i in 1 2 3 4; do (for r in 1 2 3 4; do GOMAXPROCS=1 go test ./versed/ -count=1 >/dev/null 2>&1; done) & done
go test ./versed/ -count=1        # in the foreground, while those run
```

That gives roughly 1 failing run in 2.

## It is not the gate tests

Every reproduction lands somewhere different. Across four runs:

```
TestRemovingABindingReRoutesWhatItOwned   owned by <nil> before removal, want alpha
TestTheSpineCarriesItsAnchors             the run the spine anchored has no instance to read it through
TestRunnerRemoveRefusesUntilToldWhich     context deadline exceeded
TestWatchingAgainDoesNotResetAPosition    no instance "payments-review@run-1" after waiting: map[]
TestEscalatingWhatIsNotYours              escalating another instance's question = 404, want 403
TestOverrideNamesBothParties              the record does not name both parties
```

Bindings, spine anchors, runner reachability, resolver instances, and gates. One family, and the
gate tests are simply the ones that got named first.

## The correlation is exact

Instrumented `LogdStore.Get` to print every read that returns an error, then ran the recipe above:

```
run 1: 0 failures,  0 failed reads
run 2: 1 failure , 13 failed reads
run 3: 0 failures,  0 failed reads
run 4: 1 failure , 10 failed reads
```

Repeated: 1 failure / 14 failed reads, and two clean runs with zero. A failing run always has
failed reads; a passing run never does.

## What the reads fail WITH, which rules out the obvious answer

Not `context deadline exceeded`. The tally:

```
13  context canceled
 9  session closed
 1  failed to write request: use of closed network connection
```

So it is not slowness against `sessionBudget` (10s). It is reads issued against a session that has
been torn down.

## Who is reading a closed session

Stacks on the failing reads:

```
14  trigger.            (engine loops)
10  versed.NewWithStore.func6
10  mirror.DropQuestion
10  created by trigger.
 3  versed.NewWithStore.func5
 2  resolver.Find
 1  versed.TestOneJoinerLeavingKeepsTheQuestion.func1
```

The last line is the one that says it: a goroutine belonging to `TestOneJoinerLeavingKeepsTheQuestion`
is still reading while a LATER test is running. Per-test goroutines — the engine's watch loops,
resolver machinery, mirror writers — outlive the test that created them and go on reading its
closed store. Under competing load they lag further behind, so more of them overlap the tests that
follow.

## Why that turns into a FAILED ASSERTION rather than noise

This is the half worth fixing, and it is not confined to tests.

`entity.Get`'s own doc insists on the distinction: "A failed READ is reported as an error, never as
absence... 'I could not ask' and 'it is not there' are genuinely different answers and the caller
has to be able to tell them apart." An earlier fix corrected six handlers for exactly this.

The callers here throw it away again. `versed.escalate`:

```go
q, ok, err := store.Get(mirror.QuestionRef(id))
if err != nil || !ok {
    http.Error(w, "no such question", http.StatusNotFound)
```

A read that did not happen is answered as **404 "no such question"**. That is the
`TestEscalatingWhatIsNotYours` failure verbatim — 404 where 403 was due — and it is a live defect
independent of any test: an operator escalating during a store hiccup is told the question does not
exist.

`exclusiveOwner` (server.go:2272) does the same and returns "nobody owns it", which is
`TestRemovingABindingReRoutesWhatItOwned`'s `owned by <nil>`.

Twelve sites spell `if err != nil || !ok` in non-test code: four in versed, four in trigger, one in
resolver, three in mirror.

The test helpers repeat it one layer up. `instances()` uses `Store.List`, which answers nil on a
failed read, so `waitFor` cannot tell "not minted yet" from "could not ask" and times out with
`map[]` — which is what `TestWatchingAgainDoesNotResetAPosition` reported.

## So there are two defects here, and only one is the tests'

1. **Per-test goroutines outlive their test and read its closed store.** A leak. It makes the noise,
   and it is what load amplifies. Fixing it makes the suite quiet.
2. **A failed read is rendered as absence** — in twelve non-test call sites and in the helpers. This
   is what converts the noise into a wrong answer, and it is the one that also mis-answers a real
   operator. `escalate` returning 404 for an unreadable store is the sharpest instance.

(2) is worth doing on its own terms even if (1) never happens: it is the same correction
made earlier for the read routes, applied to the sites that Get rather than List.

## What this does NOT say

It does not explain `TestOverrideNamesBothParties`'s "does not name both parties", which is this
issue's original subject and is about a record missing `overrode` after an answer. That one had
zero failed reads in its run and remains what `7b6cb09d`'s discussion describes: two writers, and a
precondition evaluated against a view that lags the answer. The analysis above is a SECOND cause
that has been reported under the same title, not a replacement for the first.
