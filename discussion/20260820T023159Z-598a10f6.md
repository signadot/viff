## What it actually depends on: how long the task takes

Same harness, the only change being a driver that takes 200ms instead of returning immediately:

    instant  20 subjects  →  675ms  (29.6/s)    149 task:run records for 20 tasks
    instant  60 subjects  → 24.45s  ( 2.5/s)   2380 task:run records for 60 tasks
    200ms    20 subjects  →  281ms  (71.3/s)     20 task:run records for 20 tasks
    200ms    60 subjects  →  1.52s  (39.4/s)    115 task:run records for 60 tasks

The quadratic is entirely the instant case, and the mechanism is legible in the run-record count.
The engine's spawn dedupe is `e.live[id]` — "a task of this id is RUNNING" — so it holds for
exactly as long as the task does. A task that finishes before its subject's own patch is visible
to the next evaluation gets fired again from the next commit in the burst, and each of those is a
fresh spawn with a fresh occurrence, hence a fresh `task:run:<id>@<rev>`. 2380 runs for 60
subjects is 40 real spawns per subject.

## So the engine loop is not the bottleneck, and that is this issue's own next step answered

With a realistic task duration, 60 concurrent spawns land and complete in 1.5 seconds through the
engine's whole spawn path — selection, claimFlight, patch, spawn, mirror, completion hook. The
observed 131-in-174s is therefore NOT the engine loop, the dispatcher, or the cascade throttle
(all three already eliminated here, and this eliminates the loop as well). It is what sits
between `e.spawn` and a running task in the real server: `spawnerFor` → `runnerFor` → the runner
→ taskd → the coderunner, with the HTTP hop, the broker registration and the frame stream.

The cheap next step now is a CPU profile of versed over the same 131 rather than another A/B: the
in-process path is measured and fast, so the remaining candidates are all in code that is easy to
sample.

## A second finding, smaller and its own thing

The re-spawn above is real behaviour and not only a harness artifact. Any rule whose task is
FASTER than the burst of commits around it — a scripted call, a cache hit, an early refusal —
does its work several times per subject, and each run is a real one. The engine's idempotence
rests on the task still being alive, which is a weaker guarantee than the deterministic id
suggests. Whether the latch should be the SUBJECT's state rather than the task's liveness is a
design question and I have not touched it; it is adjacent to an earlier issue about the other
half of the same id.
