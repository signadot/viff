Fixed by f84dc684 on `verse/task-reason` (`.worktrees/task-reason`, off local main eb7ccb51, not pushed).

Where the reason was lost: the mirror's terminal-status handling (mirror.go, drainInto) ignored the frame's `err` and read `h.Err()` instead, which for a remote runner is a second GET of the runner's snapshot. The frame on the read plane here was the one runner/http.go synthesizes when the subscribe is refused and the snapshot is terminal with a reason (`task: ""`), so the reason had already crossed once; the mirror's own read came back empty and the record said `failed` alone. Now the frame's `err` is the record's, and the handle's account fills in only where the frame carried none.

`prompt` was missing because the `verse task run` path reflected a Meta without it (a rule's spawn passes it); `driver` was never on the record. Both are on it now (RecordFields gains `driver`; instanceFromRecord reads it), and `task get` and the list read them off the record for a task on a named runner, which neither the local runtime nor the default runner can be asked about.

Test: versed/taskreason_test.go runs a task on a named runner whose event stream names the reason while its snapshot does not; red before the fix (`err <nil>`), green after. Suite green over every package but scratchpad; `make check` green. docs/task-control.md's mirrored-kinds table says `err` is mirrored on a terminal status.
