## Code-level plan

**io/github/api.go**
- `pull` gains `RequestedReviewers []user` (`json:"requested_reviewers"`) and `RequestedTeams []team` (`json:"requested_teams"`).
- New `type team struct { Slug string `json:"slug"` }`, beside `user` and `label`. A slug is unqualified (`platform`, not `acme/platform`): the API's path key and the `@org/slug` mention's second half.

**io/github/github.go**
- `pullPayload` writes `requestedReviewers` from `userLogins(p.RequestedReviewers)` and `requestedTeams` from a `teamSlugs` helper (sorted, as `userLogins` is), each only when non-empty.
- Its doc comment says what membership means: GitHub drops a reviewer once they submit a review and re-adds them on a re-request, so being in the list is "waiting on this person".
- Three writers of the `pr` entity, all through `pullPayload`, all from endpoints that answer the fields: the listing (`reflectRepo`, github.go:543, `GET /pulls`), the single read (`reflectItem`, github.go:366, `GET /pulls/{n}`), and the webhook-run path (`reflectRun`, events.go:308, `GET /commits/{sha}/pulls`). The single read's `requested_reviewers` is nullable; a null decodes to a nil slice and is omitted. The out half reads pulls and writes no `pr` entity. So the payload agrees across every pass; this is not the `comments` case.
- The webhook arm already hints the pr on `pull_request` (which carries `review_requested` and `review_request_removed`) and `pull_request_review`, so the field stays current on the targeted pass with no new subscription.
