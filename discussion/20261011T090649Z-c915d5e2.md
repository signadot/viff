On the three points, against the code as it stands.

**1. The decision is the loop's, not the agent's.** True, and it is two different things for the two drivers. For the `llm` driver the agent HAS a `push` tool (push.go, `pushTool`), offered where the environment declares destinations and `push` is in `tools:`; it is a normal tool call, derived to `push` on the resolved ref, gated, and performed by the same `push()` the finisher uses. The finisher (`pushFinisher`) is then a second path: at quiescence the loop proposes `push auto` whatever the agent did. For codex there is no first path at all: codex's tools are codex's, verse offers it none, so the finisher is the only way work leaves. The finisher exists because the push used to happen after the loop returned, where no vector saw it and no frame named the branch (push.go's header); making it an action fixed that, and made it the loop's decision rather than the agent's. The cost you name follows: the agent cannot decide whether to deliver, or what.

**2. What state the agent leaves behind.** Also true, and sharper than point 1. `commitWork` (workspace.go) commits EVERYTHING dirty with `AddWithOptions{All: true}` as `verse coderunner`, and takes the agent's own commits as they stand only when the tree is clean. So "push what I committed, keep my scratch uncommitted" cannot be expressed: the scratch is swept into the runner's commit and delivered. The rule was chosen for an agent told not to commit, so that the one commit carries the provenance trailers. The alternative is to deliver only committed work and never touch dirt, which makes the agent the author of what leaves and leaves scratch where it is. Then the brief has to say "commit what you want delivered", and the trailers need another carrier: the ref name already carries the task id (`verse/auto/<sha>/<task>`); principal and environment could ride an empty trailer commit on top, a note, or the pull request's body.

**3. Generalising the parent-child relation.** There are two seams, and they want different treatment.

- *Task process ↔ runner* (fd 5). One op, "a credential for this destination", on purpose: push.go argues that a protocol growing one op per git flow is the defect, and that releasing a capability lets the task run whatever the operation is. I would keep that as it is. It is already the general form: a secret for a declared destination, never an operation.
- *Agent ↔ task process.* For the `llm` driver the general seam exists: `harness.Tool`, a name, a schema, a `Derive` and a `Do`, which is how `push` is offered and how any further runner tool would be. For codex it does not exist yet, and codex's protocol has the hook for it: `thread/start` takes `dynamicTools` (a name, a description, a JSON schema), and codex calls one with the server request `item/tool/call` (`tool`, `arguments`, `callId`), answered with `{success, contentItems: [{type: inputText, text}]}`. Experimental in 0.162.0: the field appears when the schema is generated with `--experimental`, and the driver already declares `experimentalApi: true`. So verse's tools can be offered to codex as ordinary tool calls, each one proposed as an action in the loop exactly as an approval request is today: derived by the tool's own `Derive`, gated by the vector, performed by its `Do` in the task process, the result handed back as the call's output.

That is the generalisation I would make: one bridge in the codex driver from `harness.Tool` to `dynamicTools`, so `push`, and later `ask` or anything a runner adds, is the agent's normal call under both drivers. It answers point 1 for codex (the agent decides to push, and names the destination), and with point 2's change (deliver committed work only) it answers what state is left behind: the agent commits what it means to deliver and calls `push`; its scratch stays put.

**What that leaves to decide**, and I would rather hear it than assume:

- Does the finisher stay as a safety net that delivers only committed work when the agent never called `push`, or go entirely so that an agent that does not push delivers nothing?
- Where provenance rides once the agent authors the commits: an empty trailer commit on top, a note, the pull request, or the ref name alone.
- Whether `ask` goes to codex the same way, in place of its own `requestUserInput`.

The doc page would then walk one protocol, not two: the agent calls a tool; the loop gates it; the task process performs it, asking the runner for a credential where one is needed; the runner stages and releases; the result is on the read plane.
