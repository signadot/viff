ANALYSED, and it is three different things wearing one symptom. One is fixed (`ae9e7a43`); the
other two are the same design question and are not. Harnesses attached — drop them in `versed/`
and run `go test ./versed/ -run 'TestPsCost|TestPsRoute|TestGateCost|TestMotionCost' -v`.

`verse gate` and `verse motion` are slow too, and worse.

## 1. `verse ps` — reading a whole SYSTEM to list one KIND. Fixed.

`taskRows` asked at `verse.task` and kept the instances. But `verse.task` is also where every
RUN RECORD lives (`task:run:<id>@<rev>`, one per firing) and every claim, so the read carried all
of them across the wire and dropped them in Go.

    100 instances x 40 runs (4100 entities): GET /tasks 2.821s, for 12,900 bytes of answer
     20 instances x  0 runs (  20 entities): GET /tasks     4ms

and it is superlinear — 5x the entities cost 34x the time. The rows printed are identical.

WHY THE PREDICATE DOES NOT SAVE IT. `entity.ListAt` does ONE `Match` at the path it is handed and
walks what comes back; the `pred` runs on the result, in the server, after everything has already
been fetched. Only the PREFIX narrows. `mirror/question.go:272` already passed its kind — the
idiom was in tree, these call sites just did not use it.

Asked at `verse.task.instance` instead: **8ms**, same 100 rows. Four siblings had the same shape
and are narrowed with it — the claim sweep, the resolver-instance sweep, the task-id set behind
flow steering, and `flowtree`'s walk, which is what `verse flow` and the flows census in
`verse status` both go through.

WHAT THIS DOES NOT DO is stop the run archive growing. `73c8c1ea` already says nothing prunes it.
After this, `ps` no longer pays for it; anything that legitimately reads `verse.task` whole still
does, and the archive still grows one record per firing forever.

## 2. `verse gate` — reading every question ever asked. NOT fixed.

Already narrowed to `verse.gate.question`, so the fix above does not apply. The problem is one
level down: **pending and settled questions share one address space**, and `status == pending` is
applied after the read.

    5 pending +    0 settled: GET /gates     2ms   200
    5 pending +  200 settled: GET /gates    20ms   200
    5 pending + 2000 settled: GET /gates   792ms   200
    5 pending + 8000 settled: GET /gates  10.0s   503

The last row is the one that matters. The read exceeds the store's request budget and the docket
answers *"the store could not be read, so this answer would be an empty verse rather than the
verse: context deadline exceeded"* — which is an earlier fix doing its job, so it
fails honestly rather than showing an empty docket. But it is a docket nobody can open, and the
answer it could not afford to compute was 435 bytes.

ONE HALF IS FIXED: `listGates` escalated overdue questions and then listed them, and each of those
read the whole subtree — so every request paid twice. It now escalates over the list it already
has (39ms -> 20ms at 200 settled; 20s -> 10s at 8000). That halves a curve; it does not bend it.

## 3. `verse motion` — the same, and it puts it on the wire

`verse motion` bare reads `verse.motion.channel`, which is every motion the verse has ever
opened. A motion is durable and terminal-once (as decided before — the docket outlives the
verse), so nothing ever leaves.

    3 open +    0 settled:     4ms,     568 bytes
    3 open +  500 settled:    69ms,  93,068 bytes
    3 open + 4000 settled:   2.6s,  740,568 bytes     ← to print 3 rows

Worse than gates in one respect: gates filter in the server and answer 435 bytes, motions ship the
whole archive to the CLI and filter there. 740KB for three rows.

## The common cause, which is one sentence

**Live and settled records share an address space, and the liveness filter runs after the read.**
The store narrows by PATH — that is the whole of what `ListAt` can be told — so a listing can only
be as cheap as its address is specific. `ps` was one level too shallow and is fixed by moving
down one. Gates and motions are already as deep as the addressing goes: the next level down is the
id, and "is it still open" is not part of it.

## What would fix the other two, and I have not chosen between them

- **PUT LIVENESS IN THE PATH.** A pending question at `verse.gate.pending.<id>` and a settled one
  moved on answering; the same for a motion's `open`/`closed`. Then the docket read IS the docket,
  and it costs what it shows. It makes answering a MOVE rather than a field write, which is a real
  change to `mirror.question` and to the revoke/commit paths, and it interacts with
  an earlier design, which already proposes re-shaping a motion into a tree at
  `verse.motion.<id>` — this is an argument that lands in that decision rather than beside it.
- **LET THE STORE ANSWER A PREDICATE.** `ListAt` takes a pattern as well as a path, so
  `{status: pending}` is evaluated where the documents are. That is a substrate capability
  question, not a verse one, and it fixes every listing of this shape at once rather than one
  namespace at a time — the resolver-binding and source listings have the same structure and are
  small only because those registries are small.
- **PRUNE.** Independent of both, and named in `73c8c1ea` already for run records. It bounds the
  archive rather than making the read cheap, so it is a mitigation and not an answer — but it is
  the only one of the three that also helps the readers that legitimately want the whole subtree.

The first is the one that matches how the tree is already addressed. The second is the one that
stops this recurring. They are not exclusive.
