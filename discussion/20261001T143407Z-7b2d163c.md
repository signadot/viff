**Proposed direction for GitHub** (discussion, 2026-10-01).

- **Answering.** Reviewers answer verse's ask with commands in a PR comment (`/verse object <why>`, `/verse proceed`), and each command is an answer to the ask, given as the person who wrote it. Verse mirrors the ask's state back as its own PR review: "Request changes" while an objection stands, and "Approve" once the ask settles `proceed`. GitHub's review state is therefore an output of the ask, never an input. Two things to check: a verse approval may count toward "required approvals" (decide deliberately), and GitHub does not let a PR's author review it.
- **Identity** (GitHub login → verse principal) is not this part's to solve. It belongs to the perms work on external identities (filed separately). Until a person is mapped, their comments do not count as answers.
- **A small, plan-independent GitHub surface.** Reflect PRs and comments. Act by opening a PR, commenting, reviewing, and merging with the `sha` precondition. Check runs, commit statuses, rulesets and bypass lists are left out. Host enforcement is optional, reported if at all, and nothing depends on it. The verse-side guarantees (part 3: tag only a tree verse decided, honour only signed `live-verse.*` tags) hold on any host and any plan.
- **No GitHub App on the main path.** A GitHub App's configuration (permissions, events, webhook) lives in GitHub's settings and cannot be controlled from a repository. The manifest flow only creates an app. So the work extends the existing token-based github io, and a GitHub App io is a separate, deferred issue.
- **Open:** whether `review.<repo>.<x>` is written by an io or derived by a charter from what the github io already reflects. This is discussed next.
