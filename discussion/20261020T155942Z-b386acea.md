## Claude credentials: what a runner can run under, and what each costs

The counterpart of the codex accounts thread (Slack, 2026-10-15). Sources: code.claude.com/docs (authentication, env-vars, headless, llm-gateway-connect, legal-and-compliance, agent-sdk/overview), platform.claude.com (workspaces, workload-identity-federation); checked 2026-10-20 against Claude Code 2.1.304.

Claude Code reads its credential from its environment, or from a login under its config directory. Which one it finds decides which bill the work lands on.

**API key.** `ANTHROPIC_API_KEY`, sent as `X-Api-Key`. Usage is metered to the Console workspace that owns the key (a workspace belongs to one organisation; workspace and service-account keys outlive their creator, personal ones are archived with them). No refresh; the docs are silent on expiry. This is what the claude runner does: the key sits in the pod as the `verse-claude` Secret, the runner reads it and the task process puts it in the claude process's environment, with a `CLAUDE_CONFIG_DIR` of the task's own that is removed when the task ends. Unlike codex's login file, the key is in the process's environment, which every command Claude runs inherits; what bounds it is the run's network.

**Subscription seat.** Two forms.
- `claude setup-token` prints a one-year OAuth token for `CLAUDE_CODE_OAUTH_TOKEN` (Pro, Max, Team, Enterprise). It makes model requests only, works headless with `-p`, and does not refresh: when it expires, mint another. The runner already takes it: `claude: {credentialEnv: CLAUDE_CODE_OAUTH_TOKEN}` and a Secret holding it. Nothing to build.
- An interactive login writes `.credentials.json` (0600) under the config directory: access and refresh tokens, shape undocumented. Claude Code refreshes under a shared lock and documents the contention error when two processes refresh at once. On a runner this would need what the codex thread lists for the ChatGPT seat: a login without a desktop, durable tokens, one refresher. Not worth building while `setup-token` covers the headless case.

Precedence when several are set: `ANTHROPIC_AUTH_TOKEN` > `ANTHROPIC_API_KEY` > `apiKeyHelper` > `CLAUDE_CODE_OAUTH_TOKEN` > profile/federation > the `/login` credentials. A leftover key silently shadows a seat; the runner passes exactly one variable, so this cannot happen there.

**Whose seat.** Anthropic's terms (legal-and-compliance): "OAuth authentication is intended exclusively for purchasers of Claude … subscription plans and is designed to support ordinary use of Claude Code"; "Anthropic does not permit third-party developers to … route requests through Free, Pro, or Max plan credentials on behalf of their users"; "Customers may not pay for, resell, or intermediate Claude usage on their end users' behalf. Each end user must authenticate with their own Anthropic API key, Claude subscription plan credentials, or 3P inference provider credential." The Agent SDK page says the same of agents built on it.

So the two seat shapes read differently:
- **One seat on staging that everyone's tasks spend** is a seat intermediated for others. Not a shape to set up.
- **A developer's seat on a runner that is theirs** — their `setup-token` in that runner's Secret, the runner's permissions deciding who may spend it (who may read the runner, from the cost design `tc4qyrs0`), which is them — is their own credential for their own use. This is the shape the config is already made for: one `credentialEnv`, one runner per seat, verse recording who launched what.

**Gateway.** `ANTHROPIC_AUTH_TOKEN` (sent as `Authorization: Bearer`) with `ANTHROPIC_BASE_URL` routes through a gateway such as Portkey, with its caps. The runner passes one variable today, so a gateway needs a second (`ANTHROPIC_BASE_URL`) in the claude process's environment: a small addition to the `claude:` section if anyone wants it. `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1` is already set, so the model host is the only egress Claude asks for.

**Cloud providers.** Bedrock (`CLAUDE_CODE_USE_BEDROCK=1`, the AWS SDK credential chain), Vertex (`CLAUDE_CODE_USE_VERTEX=1`, ADC) and Foundry each take the provider's own credential. On EKS the SDK chain reaches IRSA, which would be a static-key-free shape; not tried.

**Longer term.** Anthropic's workload identity federation: a task presents a short-lived JWT (`ANTHROPIC_IDENTITY_TOKEN_FILE`, with `ANTHROPIC_FEDERATION_RULE_ID`, `ANTHROPIC_ORGANIZATION_ID`, `ANTHROPIC_SERVICE_ACCOUNT_ID`, `ANTHROPIC_WORKSPACE_ID`) and exchanges it for a token of 60s to 24h. That gives per-task attribution on Anthropic's side with no shared secret at all, and Claude Code reads those variables. It depends on a federation rule in the Console organisation and on verse's token issuer being configured, which staging has not yet done; a token with a `jti` claim is single-use.

**What a runner sees of a seat's budget.** Under seat auth the session emits `rate_limit_event` messages with utilisation and reset times (the five-hour and seven-day windows, as observed); API-key sessions get none. The runner logs them today; surfacing a seat's utilisation on the runner record is a later step.
