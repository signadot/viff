A per-task credential can just be the virtual key. That makes this much
smaller than the comment above assumes, and the driver already has the seam.

`task/harness/llm.go` sends two separate headers:

	x-<gateway>-api-key       the account key — always
	x-<gateway>-virtual-key   optional, only when set

They are already independent. So the account key stays exactly where it is, in the runner's own
environment, read from `apiKeyEnv` and never written down; and the only thing that has to travel
per task is the VIRTUAL key, which is one string in one header.

What that buys, without verse building any of it:

- **Spend has an owner** — budget, rate and routing hang off the virtual key inside the model gateway, so
  "which charter burned the quota" is answered by whoever issued the keys rather than by a budget
  system verse would have to grow. `docs/working/work/task-budget.md` still wants its stop, but
  it no longer has to also invent accounting.
- **Isolation and tiering** are a key each, not a deployment each: cheap-model triage and
  expensive review stop being two runners.
- **Rotation is cheap**, which is the property a value that rides on a task record needs.

It does NOT make the virtual key a non-secret. It is still bearer within the account — whoever
can read the record it sits on can spend against that key — so the two questions left from the
comment above are the ones that still matter, just narrowed:

- **Who may name which virtual key**, since naming the expensive one is an act with a cost. Still
  the same grants question, and still not an on-behalf-of back door (`task.Provenance` is
  deliberately not authority).
- **Where the name is chosen**: the provider entity looks right, since
  `provider.<capability>.<id>` already carries what a selected doer contributes and selection is
  already the governed step — a virtual key beside `driver`, `frame`, `tools` and `grant`.

And one narrower question this raises: whether the key is READ from the record or NAMED in it. A
virtual key on the record is the simple version; a NAME the runner resolves in its environment
keeps records free of bearer strings, at the cost of every runner knowing every key. The first is
probably right given what a virtual key is for, but it is a choice and not an accident.
