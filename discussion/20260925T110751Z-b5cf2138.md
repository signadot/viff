Two things from re-cutting the conversation plan (`ezx7sarph`, now built on an `ask` tool that raises a `gate.question`) against this design.

**When does the task end?** The result comes from `Stop`, but in an interactive session `Stop` fires at the end of every turn and the session goes on. For a charter-spawned review the first `Stop` with no `background_tasks` is plausibly the end; for a session somebody is attached to it is not, and the design does not say which. The rule that fits "the session lives as long as the task" is the runner's, not verse's: the task ends at a `Stop` with no background work and nobody attached (terminal or Remote Control), and while somebody is attached each `Stop` is a turn whose final message updates the result. Worth stating on the page, since the runner has to implement it in step 1.

**Two probes to add**, both about a question the model asks rather than a permission prompt:

1. Can a channel message (or the permission relay) answer a pending `AskUserQuestion`, or an MCP elicitation from verse's server, from outside the session? The probe showed the relay answers permission prompts with no time limit; a question Claude asks was not probed. If only an attached person can answer it, "answer from Slack or your phone" holds for permissions but not for questions, and the `ask` plan's Claude-side mapping (`AskUserQuestion` seen through `PreToolUse`, answered from the docket) does not work.
2. A verse MCP tool that blocks for a person — `ask` as an MCP tool — against Claude Code's MCP tool timeout. The hook path was probed (a 20-second stall held the dialog open); an MCP call waiting over a weekend was not. If it times out, `ask` under Claude has to be `AskUserQuestion` plus hooks, not an MCP tool.
