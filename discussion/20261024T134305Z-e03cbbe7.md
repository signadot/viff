## Plan

**An existing route changes the shape.** `POST /accounts/github/verify {nonce}` (versed/identity.go `verifyAccount`, `linkComment`) already binds from a `/verse link <nonce>` comment on any issue or pull request that a trusted github iod reflects. Verse searches the reflected comments itself, every `<root>.<org>.<name>.comment.<n>.<id>` under each trusted iod's root. docs/reference/perms.md names both routes: the iod's `heard` "when the comment replies to a question it is asking", and the person's `verify` "for a comment on any pull request the iod watches". versed/identity_test.go covers it.

Nothing calls `verify`, though. The CLI only claims (`claimThrough`, cmd/verse/login.go) and prints the line. It tells the person the verse binds "when the io reports it", which is only the `heard` route. So the route that works anywhere has no command, and the one the CLI implies works only on a questioned pull request.

### Recommended: the CLI finishes the link through `verify` (option A)

1. **`claimThrough`, for `github` only.** Print the line, then wait for the link. Every 5s, POST `/accounts/github/verify {nonce}`:
   - 201/200 prints the bound row ("linked: github foxish (12345) is user:…") and ends.
   - 404 keeps waiting. The comment is not reflected yet: it reaches the store on the webhook's hint within seconds, or on the minute resync.
   - 410 ends: the claim expired.
   - Anything else is the error.

   The wait ends at the claim's `expires`, an hour, which is the claim's own end and not a limit the tool sets. Ctrl-C stops it; claiming again gives a new nonce.

   One case: when the `heard` route binds first, through a reply on a questioned pull request, the claim is spent and `verify` answers 404 "no claim of yours". On a 404, the CLI also reads `GET /accounts` and ends when a `github` binding for the claimed login stands.
2. **The wording.** For `github`: "say this in a comment on any issue or pull request in a repository verse reflects: <repos>; this waits until verse sees it." The repos are the trusted github iods' `owns`, from `GET /iods`, which also answers Ani's first question. Slack's wording stays "a message to the app", and each provider names only its own venue. That is half of suggestion 2 in the thread, and it falls out of the same edit.
3. **Docs.**
   - docs/perms-guide.md: the GitHub sentence becomes any issue or pull request in a reflected repository, and says the command waits.
   - docs/reference/perms.md: say the CLI uses `verify`.
   - The `account` synopsis.
4. **Tests.** Extend `TestLoginLinkClaimsAnAccountAnIoProves` (cmd/verse/login_test.go), not a new test with its own server:
   - The comment is written into the store after the claim, as the reflection would write it, and the command ends linked.
   - An expired claim ends with the expiry.

   versed already covers `verify` itself.

No versed or iod change. The iod's `heard` on a questioned pull request stays as it is.

### Not recommended: the iod hears it anywhere (option B, as this issue was first written)

This would be a per-pass step in the github out half, over every reflected conversation comment in the repository, not only replies to its own question:
- an optional hook on `verseio.Out.Pass`, for one sink;
- memory of which comments it acted on (a marker in its reply, since an out half writes only statuses beside inputs);
- link handling moved out of `answerReplies`.

It adds a reply on GitHub and needs no waiting CLI, but it is about three times the code. It also duplicates a search verse already does, and only works where the iod runs `-out`.
