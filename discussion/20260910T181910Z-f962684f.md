Reproduced in a live run, 2026-09-10 18:09Z, with a cost.

The first run of the comment-drift charter reviewed 79 files across 21 commits and
found two real cases of drift. Its derive names `$item.proposedAt`; the `resolved` finding had
no such key (nothing was proposed for it), so the whole `!each` failed:

    WARN completion hook failed: the firing wrote nothing chain=review-range.onDone
    err="$item.proposedAt is not present in the payload that fired this action"

The patch had already landed. So:

  - `acme.drift.range.<tip>` says `stage: reviewed`, `status: done`, `err` cleared, and
    carries the full report including both findings;
  - `acme.drift.finding` is EMPTY;
  - the cursor advanced to the tip, so the range is never reviewed again.

The open finding is lost — not delayed, lost: `gather` hands the next review what stands in
`finding`, and nothing does. Every surface says the review succeeded. That is this issue's
'the subject latches over a write that never happened', with the twist that the warning says
'the firing wrote nothing' while the report is plainly in the store, which reads as a
contradiction to anyone holding both.

## Two fixes, and they are not alternatives

RESOLVE BEFORE WRITING closes this class. applyOne (trigger/trigger.go:774-800) expands the
patch, WRITES it, and only then resolves each derive one at a time. Every failure of this kind
— a reference that is not present — is knowable before any write. Hoisting derive resolution
above patchEntity would have made this run a clean no-op with nothing latched, and costs
nothing: the values are already computed from the same resolved root.

LOGD TX closes the residual. Even with resolution hoisted, the patch and the N derived entities
are still separate commits, so a store-side failure partway still leaves a partial. libctl has
multi-participant transactions for exactly this: `NewTx(ctx, participants)` returns an id,
`PatchTx(path, data, txID)` joins it, and the transaction commits atomically once all
participants have joined — every participant seeing the same commit. `PatchTxIf` carries a
precondition too, so the existing CAS survives.

Three things to weigh before reaching for it:

  - `PatchTx` BLOCKS until every participant joins, so applyOne cannot issue the writes in
    sequence; they have to be in flight together or the first one waits forever.
  - the participant count is fixed at NewTx, so it must be known up front — 1 patch plus N
    derived entities. That is knowable only after resolution, which is another reason to hoist
    it first.
  - entity.Store exposes no transaction today; LogdStore.Write goes straight to Patch/PatchIf.
    A store-level tx API is the actual work, and it would serve the spawn too.

Resolution-first is the cheap half and fixes what is being hit. Tx is the half that makes the
guarantee real rather than probable.
