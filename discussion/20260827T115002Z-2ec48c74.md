PARTLY FIXED (`4f0026df`), and one claim in my analysis above was WRONG — recorded here because the correction is the useful part.

## The correction

I said "the correlation is exact" between failed `store.Get` calls and failing runs, and read that as causal. It is not. Making every read failure visible — `escalate` answering 503 instead of 404, `exclusiveOwner` and `SettledBy` reporting the read — did not make the failures go away. They come back as reads that SUCCEEDED and answered not-found.

So the failed reads I measured were mostly the leaked-goroutine noise from the same analysis: prior tests' engine loops reading their closed sessions. Both are caused by load; one does not cause the other. The correlation was with the load, not between the two.

## What the fix did buy

Four real defects, none of them test-only:

- `escalate` answered **404 "no such question"** for a store it could not read — a resolver escalating during a hiccup told its question does not exist.
- `exclusiveOwner` answered "nobody owns it exclusively", which inverts the guard it feeds: the second answerer it exists to refuse was admitted, and `overriding` came out false so the record did not name both parties. That is this issue's own original symptom, reachable without any race.
- `resolver.Find` did the same one layer down — an unreadable store made an exclusive binding look advisory.
- `mirror.SettledBy` answered "nobody was here first", telling an answerer they won a race that was never read.

And two tests were genuinely racing: they asserted on `resolver` the instant `waitQuestion` returned, but a question is posted `pending` and OWNED by a second write. Same shape 7b6cb09d fixed. `waitOwned` waits for the fact under assertion.

Loaded reproduction: **6 failures in 6 runs before, 3 in 6 after.**

## What is left, now isolated

`TestOverrideNamesBothParties`, `TestAnsweringBeforeTheDeadline`, `TestTheSpineCarriesItsAnchors`. With the error-swallowing gone, these are no longer reads that failed — they are reads that succeeded and answered **not-found for an entity that was written**:

    escalate_test.go:240: the verdict was refused: 404 Not Found
    spine_test.go:239:    the run the spine anchored has no instance to read it through

`DropQuestion` marks `status: orphaned` rather than removing, so a retired question is still THERE and escalate would answer 409, not 404. A 404 means `Get` returned ok=false for a key that stands.

That is a visibility question about the store rather than a caller bug, and it is where I stopped — this repo's own guidance is to test verse's observable behaviour rather than chase logd internals. What would settle it is instrumenting `Get`'s `keyStands` tiebreak (the branch that turns a bare null into an absence) and seeing whether the not-found comes from there under load.

## The reproduction, since it was never written down

Neither CPU starvation nor parallelism alone does it. Competing load from other processes does:

```sh
for i in 1 2 3 4; do (for r in 1 2 3; do GOMAXPROCS=1 go test ./versed/ -count=1 >/dev/null 2>&1; done) & done
go test ./versed/ -count=1        # in the foreground, while those run
```
