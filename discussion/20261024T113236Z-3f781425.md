## Code-level plan

The model is `github-issue`'s comment and close (runner/runnerd/delivery/issues.go `githubIssue`): a step decided by the autonomy and the ceiling, performed with the repository's credential, answered as text.

**systems/documents/github.tony**
- `list-prs`: "Read the repository's open pull requests …", no fields beyond `repo`.
- `read-pr`: one field, `pr` (the number), as `github-issue`'s `issue` is.

**task/step.go**
- `StepGitHubListPRs = systems.Step("github", "list-prs", "repo")`
- `StepGitHubReadPR = systems.Step("github", "read-pr", "repo", "pr")`

**runner/runnerd/delivery/protocol.go**
- `Request` gains `PR string` (`tony:"field=pr,omitzero"`), and the `Op` comment names the two ops.

**runner/runnerd/delivery/github.go**
- `OpGitHubListPRs = "github.list-prs"`, `OpGitHubReadPR = "github.read-pr"`.
- `ListGitHubPRs(ctx, hc, token, api, owner, repo)`: `GET /pulls?state=open&per_page=100`, following pages to a cap of 500, and returning whether the cap cut it.
- `ReadGitHubPR(ctx, hc, token, api, owner, repo, n)`: `GET /pulls/{n}` and `GET /pulls/{n}/reviews` (100 per page, to the same kind of cap).
- A small `ghPR` decode struct: number, title, state, draft, user, base/head ref, updated_at, created_at, html_url, body, requested_reviewers, requested_teams; and `ghReview`: user, state, submitted_at.
- `githubAPI` today reads one page. Pages are followed by the `Link: rel="next"` header, so `githubAPI` gains a variant that returns the next URL. That is the one change to shared code.
- The text the task reads: one line per pull request for a list (`#123 title — author, updated …, requested: a, b; teams: x`), and for a read the fields, then the reviews one per line, then the body last, introduced as written by the author.

**runner/runnerd/delivery/server.go**
- `answer` dispatches the two ops to a new `s.githubRead(ctx, tk, req)`, which is `githubIssue`'s shape: the tree, `s.Ceilings["github"]` present, `fields` = `{repo}` plus `{pr}` for a read, `s.refused`, `RepoPath`, `tk.Credential`, then the call.
- A bad `pr` is refused as `githubIssue` refuses a bad issue number.

**runner/runnerd/verserunner/repotools.go**
- `listPRsTool`, `readPRTool` = `systems.Tool("github", …)`.
- `repoTools` appends `prReadTool(cl, ws, all, listPRsTool)` and `prReadTool(…, readPRTool)` inside `if github`.
- `prReadTool` is `githubIssueVerb`'s shape: params `repo` (enum) and `pr` for a read, `Fields` gives `repo` canonical and `pr`, `Do` relays the op.
- The descriptions say the title, body and reviews are other people's words and come into the context as written.

**All four doers get them with no change of their own:** runner.go builds one `tools` list, filtered by `offered(tools, l.Environment)`, and hands it to the verse agent (`Extra`), codex (`codex.Task`), claude (`claude.Task`, served over its MCP server) and a script (`verse-call-tool` lists tools by name).

**Ceilings:** a block naming no verbs gives every verb of the document (`given`, systems/environment.go). The three staging runners' `github: {ceiling: {repo: "github.com/signadot/**"}}` therefore grant the new verbs as they land; no deploy change. The same holds for an environment: `github: [{repo: …}]` with no verbs would also give `create-pr`, so the alert charter names its verbs.

- runner/runnerd/verserunner: extend the test that asserts which tools a GitHub runner offers, so the two names are in it and they are dropped by `offered` for an environment that gives only `create-pr`.
