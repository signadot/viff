Decided: the credential is chosen by the PROVIDER ENTITY, and the record carries a NAME
rather than a value.

	verse data provider review careful -put '{
	  driver: llm, risk: low,
	  virtualKey: review,        # a NAME this runner resolves, not a key
	  frame: "…"
	}'

The indirection is the point: a named key's VALUE changes in one place — where the runner reads
it — and every provider entity naming it follows without being rewritten. Records stay free of
bearer strings, so what a task record carries is a word, and reading the record buys nothing.

It also falls out of what is already there. `provider.<capability>.<id>` carries what a selected
doer contributes — `driver`, `frame`, `tools`, `grant` — and selection is already the governed
step, so a `virtualKey` sits beside them and is chosen by the same question. And the coderunner
already resolves names against its own config twice over: `agents` and `environments` are both
maps from a name a spawn carries to something only the runner holds.

## What this makes it, concretely

- **The provider entity** names the key. One word.
- **The runner's config** maps names to where the values live, the way `llm.apiKeyEnv` already
  does — names, not values, "so a config file that is read, copied and committed carries no
  secret".
- **The account key does not move.** `x-<gateway>-api-key` stays the runner's; only
  `x-<gateway>-virtual-key` varies per task, and `task/harness/llm.go` already sends the two
  independently.
- **A name the runner does not have is a refusal, not a fallback** — the rule
  `Config.Environment(name)` already states: "the same class of mistake as a misspelled runner
  that runs in-process". Checked at the spawn, like `MissingLLMCreds`, so a task that cannot
  finish never starts.

## What is left open

- **Who may name which key.** Naming the expensive one is an act with a cost, so it is a grants
  question — and the answer must not become on-behalf-of by a side door (`task.Provenance` is
  deliberately not authority).
- **Two runners, two key sets.** With names resolved per runner, a provider that works on one
  runner refuses on another. That is the honest behaviour, but it means "which runner can run
  this provider" becomes a real question a person will ask, and something should be able to
  answer it before a spawn rather than at one.
- **What the task record says afterwards.** The name, so spend has an owner that can be read back
  without reading a secret.
