**Decided: the gate is the install, not the merge** (2026-10-03). Supersedes the first bullet of the 2026-10-01 decision: the tag records what verse installed; it does not decide.

The problem: the flow "branch pattern → verse-managed PR with checks → verse tags and deploys" gates at the merge, and a merge is reached by many paths of which verse owns one. Anything that reaches main another way (an ordinary PR, a push, CI) is installed by whatever installs main. GitHub-side protection (CODEOWNERS on `charters/**`, a required check) narrows the paths but is invisible to verse and does not stop an admin. So the enforcement point moves.

**The invariant.** What runs in verse is the last state of `charters/**` on main that passed verse's checks and verse's ask. How it reached main does not matter. Three states, kept distinct:
- *on main*: the tree hash of `charters/**` at main's sha, which the git io's reflection of `origin/main` lets verse notice;
- *approved*: the tree hash the ask settled `proceed` on, a record verse keeps;
- *running*: what is installed, tagged `live-verse.N` as the record of the install.

**The reconciler** (a system-charter rule, level-triggered as the io docs prescribe for systems verse does not own) fires when main's sha moves, spawns a task that computes the `charters/**` diff between running and main from the git io's mirror (the io reflects refs and commits, not file contents), runs the checks, and:
- if the tree hash is already *approved*: installs, tags, no ask;
- otherwise, checks passing: raises the ask **as a pull request** from a candidate branch at main's sha onto a branch `verse/live` that verse keeps at the running sha, so the PR's diff is exactly "what is on main against what is running". The ask rides that PR through the github io; `proceed` makes verse merge it, which moves `verse/live`, installs and tags; main moving again closes it as superseded and opens the next;
- checks failing: the same PR carries the failure and stays open as the thing to fix. No separate issue.

**Approval is keyed to the tree hash of `charters/**`, not to the path in.** A change reviewed on a convention branch and merged to main arrives with the tree hash the ask already settled on, squash or not, and installs without a second ask. The `verse/live` PR therefore appears only for a change that arrived another way. The branch convention keeps its job of coordinating the normal path.

**The diff is verse's, computed from its mirror, and the PR only renders it**. `verse charter diff` shows running against main from the CLI and the ask is answerable there, so GitHub being down loses the rendering and nothing else. **An override is a recorded install**: `verse charter install` from a checkout, by a named person with a reason, sets *approved* to what was installed; the reconciler then sees main diverging and raises the usual candidate PR, so the divergence is visible and gets reconciled. An install verse did not record (a CI job calling `verse c`) is drift between running and approved; drift raises an ask and is never silently reverted.

**GitHub's protection stays as a belt**: a required status check from the verse App on PRs touching `charters/**`, so the common path hears of a failing check before the merge rather than from the candidate PR after it. Verse's checks inform GitHub's merge; GitHub's approval still never feeds verse's decision.

**What changes per part:** part 1 (j9vbwvja) keeps the approved tree hash installed and holds the installed record; part 2 (jdvbwvja) gains a second kind of review environment, the candidate PR verse opens itself; part 3 (jhvbwvja) ends at the install, its layer 2 becomes the whole mechanism and its layer 3 falls away; part 4 is untouched, a trial has a tree hash to run.

**Still open:** whether an out-of-band candidate installs on silence or waits for a spoken yes (it carries permissions), and the ask's shape in general, which the team decides together.
