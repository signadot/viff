A PROPOSED FORMAT, rendered from the real route table and the real schema rather than sketched —
the renderer is attached (`apiformat_test.go.txt`, drop it in `versed/` and run
`go test ./versed/ -run TestProposedAPIFormat -v`), so every line below is output, not a mockup.

Short version: the surface becomes a `paths:` section beside `define:`, which stays exactly as it
is. And the command that prints it should be `verse api`, absorbing `verse schema`.

## The format

```tony
context:
- tony-format/context

paths:
  /entity:
    get:    {answers: .[verse-entity]}
    post:   {request: .[verse-put-entity], answers: .[verse-entity]}
    delete: {}
  /tasks:
    get:    {answers: .[array(verse-instance)]}
    post:   {request: .[verse-spawn], answers: .[verse-spawned]}
  /tasks/{id}:
    get:    {answers: .[verse-instance]}
  /tasks/{id}/events:
    get:    {answers: !stream .[verse-frame]}
  /tasks/{id}/inbox:
    get:    {answers: .[array(verse-inbox-item)]}
  /flow/pause:
    post:   {request: .[verse-flow-steer], answers: .[verse-steered]}
  /flow/tree:
    get:    {answers: .[array(verse-flow-tree)]}
  /flows:
    get:    {answers: .[array(string)]}
  /watch:
    get:    {answers: !stream .[verse-event]}

define:            # UNCHANGED — 49 definitions, the defs section
  root: …
  verse-action: …
  verse-entity: …

signature:
  name: root
```

Three things it is doing deliberately:

  - **GROUPED BY PATH, methods under it.** That is OpenAPI's shape, and it is the one that reads:
    every method on `/charter/{name}` together, rather than scattered through a 51-element flat
    list the way `GET /api` serves them today.
  - **ONE TYPE LANGUAGE.** `request:` and `answers:` are written as the same `.[name]` expressions
    `define:` already uses, so resolving a response is a lookup in the same document. No second
    notation, no `$ref`.
  - **`Returns` DOES THE WORK OpenAPI needs ceremony for.** `.[array(verse-instance)]` and
    `!stream .[verse-frame]` come straight from `returns: list` and `returns: stream`. A stream is
    a first-class answer here, where OpenAPI has to describe SSE out of band or lie about it.

## The command: `verse api`, replacing `verse schema`

The disambiguation falls out for free — the leading `/` decides:

```sh
verse api                    # the whole document: paths, then define
verse api /tasks             # one path, its methods and their types
verse api verse-entity       # one definition, which is `verse schema <name>` today
```

That is the discrimination-by-spelling this tree already uses elsewhere (a step beginning `[` IS
an access; `Ref.String` only ever puts a colon in the last segment). One command, one grammar.

`GET /api` is a served route with no CLI verb at all today, so this gives it one rather than adding
a thirteenth command beside `verse schema`.

## What to watch, and it is the design point

`root.tony` records that the surface used to be DERIVED from versed's route table, and that it was
moved out deliberately: "which made it unable to lie and also made the whole schema unobtainable
without a server. Now the schema stands alone and the API is what has to agree with it, which is a
test (TestTheRootIsTheServedSurface) rather than a construction."

Naming the command `api` pulls the other way — a reader will expect it to reflect the RUNNING
server. Both can be true, but only if `paths:` is declared in package `schema` (a `paths.tony`
beside `root.tony`, or a checked-in generated artifact) with `TestTheRootIsTheServedSurface`
extended to hold it equal to the route table. Source it from `s.routes` instead and `verse api`
stops working without a verse up, which is a property that was paid for once already.

## The honest gap, which is larger than the format

**25 of the 51 routes say nothing at all.** Not a rendering problem — there is nothing to render:

```
/gates:              get: {}
/charter:            get: {}   post: {request: .[verse-trigger]}
/resolvers:          get: {}   post: {}
/runners:            get: {}   post: {}
/sources:            get: {}   post: {}
/tasks/{id}/cancel:  post: {}
/schema:             get: {}
```

`root.tony` already gives the reasons for several: `gates` rows "are still assembled as map
literals, so there is no named shape to point at"; `charter` is a document the server BUILDS
rather than a struct's wire form; `schema` is its own unnamed shape. So an OpenAPI-ish artifact
ships half-empty until those handlers answer in named types. That is the actual work behind this
issue; the format is the easy half, and it is worth deciding whether the format lands first (and
fills in as types arrive) or waits.

## Two gaps worth leaving room for NOW rather than retrofitting

**QUERY PARAMETERS are described nowhere.** Counted in `versed/server.go`: `scope` x7, `at` x5,
`since` x3, plus `sub`, `if`, `runner`, `subject`. `verse data --at` rides one, `--scope` rides one
on nearly every route, and none of them appear in any published artifact. They belong inside the
method map:

```tony
  /entity:
    get:
      query:   {at: .[string], scope: .[string]}
      answers: .[verse-entity]
```

**STATUS CODES are not published either**, and they are load-bearing: 409 for a refused
precondition and for a write that would replace what it descends through, 503 for an unreadable
store, 502 for a runner that did not answer. A sibling key keeps `answers` meaning the 200:

```tony
      answers: .[verse-entity]
      refuses: {409: "a precondition did not hold", 503: "the store could not be read"}
```

Both are additive to the shape above, which is why they are worth naming now — adding them later
is a reshape of every method map.

## What this does not propose

Emitting literal OpenAPI JSON. The issue says "something LIKE an openapi spec", and the value is
the shape — paths over defs — not the serialization. A verse publishes tony; a converter to
OpenAPI is a downstream tool that has everything it needs once `paths:` exists, and it can live
outside this repo.
