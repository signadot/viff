Fixed in e9545d9de, on main.

The engine's side of "a place that acts is installed as somebody's, or not at all" is the pass vetting a rule as whose it is. A rule placed from its record is now vetted as the owner on its record, or held for the record where it has none (`trigger.Engine.asOwner`), instead of being vetted as nobody and armed. The install kicks once its record is in, as it did, and that pass arms the rule over the same backlog, as its owner.

What the earlier review listed against holding, as it stands in the code:

- The install's answer: the hold is a passing cause, so `passed` and `Ready` wait through it as they wait for the pass. The record is written before `followed` returns (the take, or the record a person's write leaves inside `Store.Write`), and is in this process's view when the kick's pass runs.
- Scope engines: `applyCharter` places only records stamped with the engine's own scope and address, so a scope or package engine holds only rules installed through it, and every such install kicks it.
- A mirror read error holds the rule on that read (`causeRead`), as every other read the vetting needs does; the next pass clears it. A store that attributes nothing holds for nothing.
- A record landing with no kick: the undo of a prune now restores the record before the rule, so the rule is placed under it. A record landing by any other path (`verse perms` on a store written by hand) arms the rule at the next pass, within `reconcileEvery` — where before it fired as nobody until a restart.

The test is the one from the thread, `TestASystemRuleInstalledOverDataThatStandsActsOnIt`: the owner record is still a write of its own, so the delay still lands between the rule and its record. It fails on main with staging's refusal and passes 3/3 with the fix.
