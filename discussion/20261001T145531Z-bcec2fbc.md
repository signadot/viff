**The review-github package contract, a draft, and what it depends on.** (Discussion, 2026-10-01.)

**Depends on 84a83gkw** ("io: a sink is written by any package and read by no charter"). Today a package may write only inside its own address, and an io's out half reads only inside its claim. So a package cannot ask an io to act, and every such rule is baseline's (gate-ask, deploy-announce); strata overlap is how the second one was refused. review-github as a package needs 84a83gkw's sinks. That gap is general, not review-specific, so we could close it as its own piece of work first. Doing so also lets gate-ask and deploy-announce leave baseline.

**Places, one writer each:**
- The flow's proposal record, keyed by branch, e.g. `repo-charters.<repo>.proposal."<branch>"`, written by the flow (part 3). It holds what the flow wants: `want: open | merged | closed`, `merge: <sha>`, and `post: {<key>: text}`.
- `review.<repo>."<branch>"`, written by review-github. It holds what the review is: `kind, head, state, url, merged: {sha, by}`.
- `github.<org>.<name>.out."<review-github's address>".…`, written by review-github (a sink under 84a83gkw). It holds what GitHub is asked to do.
- `github.<org>.<name>.pr.*` and `….comment.*`, written by the github io (exists). They hold what GitHub knows.

**Flow → package.** review-github derives sink inputs from the proposal record: open (or adopt) a PR for the branch, keep one comment per `post` key, merge at `merge`, close. It is level-triggered, as gate-ask is.

**Package → flow.** Under 84a83gkw nothing reads a sink, so `~status` is not readable. review-github derives `review.*` from the PR reflection. A rule on `github.<org>.<name>.pr.*` finds its proposal with `!get-path {at: [repo-charters, <repo>, proposal, $subject.value.head]}`, because the proposal is keyed by branch. The flow judges a merge by the reflection showing `merged` at the sha it asked for, not by a status. A failed send is visible to people (`verse data`, `verse io`), not to rules.

**The ask.** The flow raises its readiness ask `about: review.<repo>."<branch>"`, with labels naming the review. A review-github rule, like gate-ask-channel, derives `{to: pr.<n>, asks: <id>}` into the sink, reading `n` from `review.*`. The io then does for `asks` what the Slack io does:
- draws the comment from the ask's record each pass;
- reads `/verse …` commands on the PR and answers as their authors (identity: 8q4azhtj);
- mirrors the ask's state as its own PR review.

**Gaps:**
- the github io's out half (open or adopt a PR, a comment kept updated, `asks`, merge at `sha`, close);
- whether the PR reflection says who merged;
- identity (8q4azhtj).

**Open:**
- Requests as fields of the proposal record, or as separate request entities. Since statuses are unreadable under 84a83gkw, separate entities buy less than they would otherwise.
- Whether the mirrored PR review is part of the io's rendering of `asks` (leaning that way) or a separate input.
