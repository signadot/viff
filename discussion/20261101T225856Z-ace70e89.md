Fixed in 5e1af4c6c, on `verse/owned-rules` in `.worktrees/owned-rules`, local and unpushed.

A rule or stratum that an install creates is now written with `Write.Grants` holding the default grants. The node and its owner record land in one commit, through the existing `withRecord` path. A rule that already stands is written as before, and `takeForTheSystem` still runs when somebody else's record stood at the name. The change is confined to the trigger package (`writeOwned` in trigger/charter.go); entity is unchanged.

This issue's text said a person's install has no gap. That is wrong: a person's install also wrote the owner record after the commit. The same write now covers both.

The test, `TestASystemRuleInstalledOverDataThatStandsActsOnIt` (versed/systemcharters_test.go), delays the separate write of the rule's record, which is slow the way staging's store is. Without the fix it fails with staging's refusal ("holds nothing … no owner on record"). With the fix it passes, since there is no separate write left to delay.
