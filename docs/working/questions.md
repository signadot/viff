Discussion on correlation of entities across different systems: a git commit, which then becomes a PR which becomes a tag, etc. How do all these IDs live in a flow?
On derived facts: verse actually has more here than I initially thought: derive writes computed entities and strata prevent cycles. But it only fires when the rule fires, so a derived value can go stale if its inputs change some other way. The question is whether we need proper view semantics where derived facts recompute whenever inputs change, or whether event-driven is good enough.
Writes inside an entity are safe mechanically (merges and CAS mean no lost updates), but nothing says who's allowed to write a given field, so two rules can both patch stage and it's silently legal. I'm not sure this needs solving now, but it may bite eventually.
Attribution: --as is just self-reported, and entity writes don't record an author at all. I think login and RBAC can come later, but policies, permissions & subjects that we've learned from building RBAC might be things to place into the model early because we're designing a system that's meant to orchestrate across systems.
Last one, smaller: if a charter spawns a capability nobody provides, you find out at first firing rather than at install? Install already catches syntax errors, so extending that to "this has no doer" would be a cheap typecheck-ish win.
Flows are instances of an SDLC-related procedure created from charters (state machines) and have goals, and flows may advance towards goals by executing tasks. Is this a correct statement?
We may need to go deeper soon into what it means to "trace" the flow - what context it will store and how we're trying to observe a flow. I think this is one of the key contributions of something like verse - to be the decision log + lineage tracker for each flow.
