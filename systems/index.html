Systems#

A system is something outside verse that verse reads or acts on: a repository, its issue tracker, a forge, Linear, Slack. The verse system is verse itself, acted on by a task as the person it runs for would. Verse meets each system in two places (basic concepts):

  • An iod connects the system to the store. It writes what the system holds into the store, where a charter reads it. It also carries what a charter writes back out to the system: a comment, a tag, a message.
  • A runner performs the system's verbs for a task. The task calls a verb, and the runner makes the call with its own credential.

Verse keeps one document for each system, at verse.systems.<name>. The document names the system's verbs and the params of each verb:

verse d verse systems git-issue

A verb is written three ways, one for each reader:

Spelling Example Who reads it
the tool, <system>-<verb> git-issue-push the task that calls it: an agent, or a script with verse-call-tool
the step, <system>.<verb> git-issue.push the task's environment, which gives it, and its autonomy, whose rows match it by its params
the row, {system, verb, <params>} {system: git-issue, verb: push, repo: github.com/acme/app} the author of a spawn, and the operator who writes the runner's ceiling

A task's events and its questions name the step and its params. So you can see what the task called, which row decided it, and what happened.

A block gives verbs#

A spawn's environment.systems gives a task what it may do, one block per system (or per repository, for the systems that name one). A block names the verbs it gives, each with its shapes: git: {repo: acme/app, fetch: {}, push: {ref: !regexp "^refs/heads/verse/"}}.

A block that names no verb gives every verb of its system, any call: files: {}, question: {}, git-issue: {repo: acme/app}. Once one verb is written, only the verbs written are given: git-issue: {repo: acme/app, pull: {}} gives pull alone. The network is apart: network: {mode: open} is its mode, and under allow its tcp-client shapes name the hosts.

A runner's ceiling is written the same way, and an empty ceiling block allows every verb of its system. A git block can be written empty too, and then gives every push, forced or deleting, of any branch; a charter that ships writes its git push shapes instead.

System Verbs Its iod
git push, fetch iod git
git-issue create, comment, close, pull, push iod git-issue
github create-pr, update-pr, list-prs, read-pr, comment-pr, reply-comment iod github
github-issue create, comment, close iod github
linear-issue create, comment, close iod linear
slack post, reply, read, react iod slack
secret exec none: one command the runner runs with a secret of its store, which the task never holds
mcp call none: the tools of a remote MCP server the operator names, called by the runner with the server's credential
pkg install none: a package the runner installs into the task's read-only prefix, from the signed repositories the operator trusts
verse ask-create, ask-get, ask-list, data-get, data-put, data-rm, charter-get, charter-check, charter-install, charter-remove none: verse itself, reached through the runner's own token
question ask none: a question goes to the docket (asking)
files, commands, agent write; run; call-sub-agent none: these are what an agent does inside its run
network tcp-client none: the connections a run opens through its runner's proxy

The runner performs the verbs of git, git-issue, github, github-issue, linear-issue, slack, secret, mcp and verse. It uses its own credential, and stays within the ceiling its configuration puts over each system (the verse runner).

What a task lacks#

Three of the systems exist for what a task's image and its own hands do not give it, and they are one design read three ways. A tool the image does not carry is pkg's: the runner installs it into the task's read-only prefix, and the tool then runs inside the task, as the task's own. A command that needs a credential is secret's: the runner runs it once, in a sandbox of its own, with one secret of its store, which the task never holds. A remote service's tools are mcp's: the runner calls them with the server's credential, and the task never reaches the server. In each the task only asks; the same environment, autonomy and ceiling grammar decides; and the trust is the runner's, never the task's — the secret store under secret and mcp, and for pkg the signed index of the repositories the operator names, so that system holds no credential at all. None has an iod: these are what a task does, decided as it is done, not something verse watches.
