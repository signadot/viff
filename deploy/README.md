# Deploying verse to Kubernetes

A checked-in [`o build`](https://github.com/signadot/tony-format) — edit it here, render with
`o`, apply with `kubectl`. (Kept in the tree rather than generated by a CLI so it stays in
step with versed's flags/ports and is trivial to tweak.)

## Topology

Two tiers, split so the storage fragility stays off the engine:

- **docd** — a `StatefulSet` (1 replica) running `o sys up` (logd+docd) on a `/data` volume.
  The stateful tier: it owns durable state and, on a cloud volume, is AZ-pinned.
- **versed** — a `Deployment` (1 replica, `Recreate`) running `verse up --docd-addr …`. A
  stateless singleton engine that *attaches* to docd and floats (any node/AZ, fast restart).
  Singleton because two engines would double-fire triggers; leader-election is the scale-out
  answer later.

Plus a headless `Service` for docd (client+mount), a `Service` for the versed API, and — when
`brokerFace` — one for the broker face.

Optionally a third tier: **source connectors**, one `Deployment` + `Service` each, running
`sourced` (git, Slack, Linear). Each is a singleton for the reason versed is — a source is the
single writer of its slice — and each is off by default. See [Sources](#sources-optional).

## Build the image

The `Makefile` at the module root builds the Go binaries **locally** (fast, your host build
cache) and `docker build` only COPYs them in — no `go build` inside Docker. From `verse/`:

```sh
make docker                       # cross-compile linux binaries + build verse:dev
make load                         # + load into minikube (Docker Desktop needs no load)
make push PUSH_IMAGE=signadot/verse:latest   # + push to a registry
make docker IMAGE_ARCH=amd64      # target amd64 nodes (default: your host arch)
```

`make deploy PROFILE=minikube HOSTPATH=/Users/<you>/.verse/minikube-default` renders and
applies in one step (`make help` lists all targets). The image bundles `verse`, the pinned
`o` (which docd's pod runs), `sourced` (the source connectors), and `git` — one image, several
roles, so there is one ref to pin and one build to cache.

## Render + apply

```sh
o build deploy | kubectl apply -f -                          # defaults (dynamic PVC)
o build deploy -p minikube -e image=verse:dev | kubectl apply -f -
o build deploy -p staging | kubectl apply -f -               # EKS spot + EBS
o build deploy -s                                            # show the resolved env
```

## Storage (per profile)

The docd `StatefulSet` always uses a `volumeClaimTemplate` (PVC); only what **backs** the
PVC varies by profile:

| profile | PVC backing | notes |
|---|---|---|
| default | dynamic | cluster default StorageClass |
| **minikube** | static hostPath PV | data on your laptop fs — survives pod restarts, Docker Desktop stop/start, **and** `minikube delete`; browsable |
| **staging** | dynamic EBS gp3 | the cluster's own `gp3` SC, docd on the `stateful` node pool |

**minikube** — docd's data lives on your **laptop fs** (the only place that survives
`minikube delete`), reached through a mount. Configure the mount **once** in your shell so a
bare `minikube start` applies it (minikube binds start flags to `MINIKUBE_*` env vars — no
`--mount` args ever):

```sh
# ~/.zshrc — set once
export MINIKUBE_MOUNT=true
export MINIKUBE_MOUNT_STRING="$HOME/.verse/minikube-default:/mnt/verse"
```

Then it's just:

```sh
minikube start                    # mounts ~/.verse/minikube-default → /mnt/verse (no args)
make load                         # minikube needs the image loaded
make deploy PROFILE=minikube      # hostPath PV at /mnt/verse — data lands in ~/.verse/minikube-default
```

docd's data is now at `~/.verse/minikube-default` on your Mac — browsable, and it outlives the
cluster. (The minikube profile sets `hostPV: true`, `hostPath: /mnt/verse`.)

(9p can be slow/flaky — this is only worth it when you actually want to browse the data.)

> ⚠️ **Changing the storage backing needs a PVC reset.** A `StatefulSet`'s
> `volumeClaimTemplate` is immutable and its PVC persists, so switching backing (default SC
> ↔ `hostPV`, or a class change) does **not** rebind an existing `data-docd-0` — it silently
> keeps the old volume (e.g. stays on `standard` instead of the hostPath PV). Reset it:
> ```sh
> kubectl -n verse delete statefulset docd
> kubectl -n verse delete pvc data-docd-0
> make deploy PROFILE=minikube          # fresh PVC binds to the intended PV
> kubectl -n verse get pvc              # confirm data-docd-0 → the PV you expect
> ```

**staging (EKS)** — docd lands on the cluster's dedicated `stateful` node pool (on-demand),
on a dynamic volume from the cluster's `gp3` StorageClass; versed prefers `SPOT` and floats
over the rest. The pool is *reserved*, not merely labelled — its nodes carry a
`signadot.com/pool=stateful:NoSchedule` taint — so docd needs both halves: the `nodeSelector`
to go there and the matching toleration to be let in. That is what `docdPool` emits.

Nothing here creates the class or the pool; the cluster has both. On a cluster that has
neither, `-e emitStorageClass=true` emits a `verse-gp3` class (`WaitForFirstConsumer` → the
pod is auto-affinitized to the volume's AZ), which needs the [EBS CSI driver addon] with
node-role IAM to create/attach volumes — otherwise the PVC stays `Pending`.

[EBS CSI driver addon]: https://docs.aws.amazon.com/eks/latest/userguide/ebs-csi.html

## Knobs (`build.tony` `env`; override with `-e` or a profile)

| key | default | meaning |
|---|---|---|
| `namespace` | `verse` | target namespace |
| `image` | `signadot/verse:latest` | full image ref incl. tag |
| `brokerFace` | `true` | serve + expose the broker face; `false` drops its Service |
| `storageClassName` | `""` | PVC class; `""` = cluster default (staging sets `gp3`) |
| `storageSize` | `10Gi` | docd volume size |
| `emitStorageClass` | `false` | emit a `verse-gp3` StorageClass |
| `hostPV` | `false` | back the PVC with a static hostPath `PersistentVolume` (minikube) |
| `hostPath` | `/mnt/verse` | the PV's in-VM host path when `hostPV` |
| `docdPool` | `""` | put docd on the `signadot.com/pool=<x>` nodes, tolerating their taint |
| `spotVersed` | `false` | let versed prefer `eks.amazonaws.com/capacityType: SPOT` |
| the source knobs | off | see [Sources](#sources-optional) |

## Sources (optional)

What reflects an external system into the verse ([docs/sources.md](../docs/sources.md)). Three
are shipped, each its own Deployment + Service, each **off by default** and turned on
independently — the git one costs a clone, the other two cost a credential in the cluster.

```sh
make deploy E='-e gitSource=true'
o build deploy -e slackSource=true -e linearSource=true | kubectl apply -f -
```

They run `sourced`, the connector binary in the same image
([docs/reference/sourced.md](../docs/reference/sourced.md) is its surface). Deploying one does
**not** install it: an install carries an ownership claim verse proves against what is already
standing, so it stays a verb somebody runs.

```sh
kubectl -n verse exec deploy/versed -- verse source add git:cluster    http://git-source:9801
kubectl -n verse exec deploy/versed -- verse source add slack:workspace http://slack-source:9801
kubectl -n verse exec deploy/versed -- verse source add linear:teams   http://linear-source:9801
kubectl -n verse exec deploy/versed -- verse source
```

⚠️ **The name has to match `<x>SourceName`.** The hint url is baked into the pod
(`http://verse:9797/sources/slack/<name>/hint`), so a registration under a different name means
verse 404s every delivery — loud, but only if you look.

### Credentials

The two that need one take it from a Secret, and `optional` is **false** on purpose: a Slack
source with no token has nothing to reflect, so it fails to start rather than installing clean
and failing every pass.

```sh
kubectl -n verse create secret generic verse-slack \
  --from-literal=SLACK_BOT_TOKEN=xoxb-… \
  --from-literal=SLACK_SIGNING_SECRET=…

kubectl -n verse create secret generic verse-linear \
  --from-literal=LINEAR_API_KEY=lin_api_… \
  --from-literal=LINEAR_WEBHOOK_SECRET=…
```

### Webhooks

verse dials a source, and the source dials verse — only the *delivery* leg comes from the
internet, and only the two SaaS sources have one. Set a host and an Ingress is emitted for it;
leave it empty and there is none, and the source converges on the periodic resync (one minute)
instead of on delivery.

```sh
o build deploy -e slackSource=true -e slackWebhookHost=slack.verse.example.com \
               -e ingressClassName=nginx | kubectl apply -f -
```

Then point Slack's Event Subscriptions request url at `https://<host>/slack/events`, and
Linear's Settings → API → Webhooks at `https://<host>/linear/webhook`. Each source verifies its
own signature; verse never sees the delivery.

### A private mirror needs a credential

The git connector mounts a `verse-git` Secret at `/git-credentials`, `optional: true`, and
points git's credential helper at it. No Secret means an empty mount, a helper that answers
nothing, and an anonymous clone — which is what a public mirror wants — so there is no knob to
set for the common case.

```sh
kubectl -n verse create secret generic verse-git \
  --from-literal=credential=$'username=x-access-token\npassword=<PAT>\n'
```

The token is in a Secret rather than in the `-mirror` url because the url is in the pod spec,
and a pod spec is not a secret. The helper is read-only on purpose: `credential.helper=store`
writes the file back on success *and* on failure, so against a read-only mount it spends a
1000ms lock timeout and prints a fatal-looking line on every clone and every fetch.

⚠️ **The shipped `gitMirror` default is `signadot/verse`, which is private** — so the connector
crash-loops until that Secret exists, with git's own "could not read Username" in the log.

### The git source has no repositories

A pod has none, so `-mirror` makes one: it clones the remote at startup and fetches on every
pass. That is the read — nothing is ever pushed. The mirror lives on an `emptyDir`, so a restart
re-clones; swap in a PVC if that gets expensive. For a repository that already exists somewhere,
run the same binary next to it with `-repo`, or skip the deployment entirely and use
`verse source add --dir`.

| knob | default | meaning |
|---|---|---|
| `gitSource` | `false` | deploy the git connector |
| `gitMirror` | the verse repo | `[<id>=]<url>` to mirror |
| `slackSource` | `false` | deploy the Slack connector (needs the `verse-slack` Secret) |
| `slackSourceName` | `workspace` | the registration name — must match `verse source add slack:<name>` |
| `slackWorkspace` | `""` | the id prefix; `""` takes the team name from the token |
| `slackWebhookHost` | `""` | Ingress host for `/slack/events`; `""` emits none |
| `linearSource` | `false` | deploy the Linear connector (needs the `verse-linear` Secret) |
| `linearSourceName` | `teams` | the registration name |
| `linearTeams` | `""` | comma-separated team keys; `""` is every team the credential sees. Quote it: `-e 'linearTeams="ENG,OPS"'` |
| `linearWebhookHost` | `""` | Ingress host for `/linear/webhook` |
| `ingressClassName` | `""` | class for both Ingresses; `""` leaves the cluster default |

## LLM creds (optional)

versed does `envFrom` a `verse-llm` Secret (`optional: true`), so it deploys and runs on the
credential-free `scripted` driver without it. For `llm`-driver agents:

```sh
kubectl -n verse create secret generic verse-llm \
  --from-literal=PORTKEY_API_KEY=... \
  --from-literal=PORTKEY_VIRTUAL_KEY=... \
  --from-literal=OPENAI_MODEL=gpt-4o
```
