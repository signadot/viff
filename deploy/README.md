# Deploying viff to Kubernetes

A checked-in [`o build`](https://github.com/signadot/tony-format) — edit it here, render with
`o`, apply with `kubectl`. (Kept in the tree rather than generated by a CLI so it stays in
step with viffd's flags/ports and is trivial to tweak.) The parts it deploys, and the knob that
fills in each, are the Kubernetes column of
[What a deployment is](../docs/platform/deployment.md).

## Topology

Two tiers, split so the storage fragility stays off the engine:

- **docd** — a `StatefulSet` (1 replica) running `o sys up` (logd+docd) on a `/data` volume.
  The stateful tier: it owns durable state and, on a cloud volume, is AZ-pinned.
- **viffd** — a `Deployment` (1 replica, `Recreate`) running `viff up -docd-addr …`. A
  stateless singleton engine that *attaches* to docd and floats (any node/AZ, fast restart).
  Singleton because two engines would double-fire triggers; leader-election is the scale-out
  answer later.

Plus a `Service` for the viffd API, and two for docd, because a face is the unit anything
grants or reaches:

| | |
|---|---|
| `docd` | the client face (7071) — the store, read/write; what viffd is pointed at |
| `docd-headless` | the StatefulSet's governing Service. Nobody dials it; it exists so `docd-0` has a stable per-pod name |

> ⚠️ **An existing deploy needs the StatefulSet recreated once.** `docd` used to be the
> headless governing Service, and `spec.serviceName` is immutable — so an apply over a
> StatefulSet that still names it fails with `Forbidden: updates to statefulset spec ... are
> forbidden`. Drop it and reapply; the PVC and the data are untouched:
> ```sh
> kubectl -n viff delete statefulset docd     # NOT the pvc — data-docd-0 survives
> kubectl -n viff delete service docd         # was headless; comes back as the client face
> o build deploy -O yaml -p <profile> | kubectl apply -f -
> ```

Optionally a third tier: **iods**, one `Deployment` + `Service` each, running `iod` (git,
git-issue, Slack, Linear, GitHub). Each is a singleton for the reason viffd is — an iod is
the single writer of its slice — and each is off by default. See [Iods](#iods-optional).

## Build the image

The `Makefile` at the module root builds the Go binaries **locally** (fast, your host build
cache) and `docker build` only COPYs them in — no `go build` inside Docker. From `viff/`:

```sh
make docker                       # cross-compile linux binaries + build viff:dev
make load                         # + load into minikube (Docker Desktop needs no load)
make push PUSH_IMAGE=signadot/viff:latest   # + push to a registry
make docker IMAGE_ARCH=amd64      # target amd64 nodes (default: your host arch)
```

`make deploy PROFILE=minikube HOSTPATH=/Users/<you>/.viff/minikube-default` renders and
applies in one step (`make help` lists all targets). The image bundles `viff`, the pinned
`o` (which docd's pod runs), `iod` (the iods), and `git` — one image, several
roles, so there is one ref to pin and one build to cache.

## Render + apply

```sh
make deploy                                    # defaults (dynamic PVC)
make deploy PROFILE=minikube
make deploy PROFILE=eks                        # EKS + EBS; the profile's values are placeholders
make deploy PROFILE=/path/to/profile.tony      # a profile kept outside this repository
o build deploy -s                              # show the resolved env, apply nothing
```

A profile is a name under `deploy/profiles/`, or a file: `o build -p` takes either. The two
checked in are shapes, `minikube` for a laptop and `eks` for a cluster with the values left as
placeholders. A deployment with values of its own — its cluster, its registry, its secret
entries — keeps its profile outside this repository and passes the path. That is how this
directory is meant to be run: the build and the manifests here, the values there. The knobs that
name a file (`systemCharter`, `authConfig`, `runnerConfig` and the other two runners') read a path
relative to `deploy/`, or an absolute one, which is how a deployment keeps those files beside its
profile rather than under `deploy/`.

Prefer `make deploy` over piping `o` into `kubectl` by hand, for two reasons that are easy to
get wrong once each:

- **`-O yaml`.** `o`'s default output is *tony*, which for block-style input happens to be
  valid YAML too — so a hand-rolled pipe works until a manifest uses flow mappings, and then
  `kubectl` refuses the whole stream over a line in a document nobody wrote.
- **The cluster.** `kubectl apply` goes wherever your shell's current context points, which
  makes a hand-rolled pipe a function of ambient state — and the command that deploys one
  cluster is character for character the command that deploys another. A profile
  names its cluster in `kubeContext`, `make deploy` passes it explicitly, and it prints where
  it is going before it goes:

```
deploy: profile '/path/to/profile.tony' → context '<the profile's kubeContext>'
```

`CONTEXT=` overrides that, for the same shape of cluster under a different kubeconfig name.
An empty `kubeContext` — the default, and minikube — falls back to the current context. The eks
profile ships a placeholder instead, which `make deploy` refuses until it is filled in or
`CONTEXT=` says where.

## Storage (per profile)

The docd `StatefulSet` always uses a `volumeClaimTemplate` (PVC); only what **backs** the
PVC varies by profile:

| profile | PVC backing | notes |
|---|---|---|
| default | dynamic | cluster default StorageClass |
| **minikube** | static hostPath PV | data on your laptop fs — survives pod restarts, Docker Desktop stop/start, **and** `minikube delete`; browsable |
| **eks** | dynamic EBS gp3 | the cluster's `gp3` SC; `docdPool` puts docd on a dedicated node pool |

**minikube** — docd's data lives on your **laptop fs** (the only place that survives
`minikube delete`), reached through a mount. Configure the mount **once** in your shell so a
bare `minikube start` applies it (minikube binds start flags to `MINIKUBE_*` env vars — no
`--mount` args ever):

```sh
# ~/.zshrc — set once
export MINIKUBE_MOUNT=true
export MINIKUBE_MOUNT_STRING="$HOME/.viff/minikube-default:/mnt/viff"
```

Then it's just:

```sh
minikube start                    # mounts ~/.viff/minikube-default → /mnt/viff (no args)
make load                         # minikube needs the image loaded
make deploy PROFILE=minikube      # hostPath PV at /mnt/viff — data lands in ~/.viff/minikube-default
```

docd's data is now at `~/.viff/minikube-default` on your Mac — browsable, and it outlives the
cluster. (The minikube profile sets `hostPV: true`, `hostPath: /mnt/viff`.)

(9p can be slow/flaky — this is only worth it when you actually want to browse the data.)

> ⚠️ **Changing the storage backing needs a PVC reset.** A `StatefulSet`'s
> `volumeClaimTemplate` is immutable and its PVC persists, so switching backing (default SC
> ↔ `hostPV`, or a class change) does **not** rebind an existing `data-docd-0` — it silently
> keeps the old volume (e.g. stays on `standard` instead of the hostPath PV). Reset it:
> ```sh
> kubectl -n viff delete statefulset docd
> kubectl -n viff delete pvc data-docd-0
> make deploy PROFILE=minikube          # fresh PVC binds to the intended PV
> kubectl -n viff get pvc              # confirm data-docd-0 → the PV you expect
> ```

> ⚠️ **Changing `storageSize` needs an orphan delete, not a reset.** The apply of a changed
> `volumeClaimTemplate` is refused (`spec: Forbidden: updates to statefulset spec for fields
> other than …`). On a class that allows expansion (EBS `gp3` does), grow the claim that
> stands and let the StatefulSet be recreated around it, keeping the pod and the data:
> ```sh
> kubectl --context <ctx> -n viff patch pvc data-docd-0 -p '{"spec":{"resources":{"requests":{"storage":"30Gi"}}}}'
> kubectl --context <ctx> -n viff delete statefulset docd --cascade=orphan
> make deploy PROFILE=eks               # recreates docd with the new template; it takes over docd-0 and its claim
> ```
> An EBS volume never shrinks, and is modified at most once every six hours.

**eks (EKS)** — docd on a dynamic volume from the cluster's `gp3` StorageClass; viffd may
prefer `SPOT` (`spotViffd`) and float over the rest. A deployment that reserves a node pool for
the stateful tier names it with `docdPool`: the pool's nodes carry a
`<docdPoolLabel>=<x>:NoSchedule` taint (`viff/pool` unless `docdPoolLabel` says), so docd needs both halves, the `nodeSelector` to go
there and the matching toleration to be let in, and that is what the knob emits. `make deploy`
refuses a `docdPool` with an empty `docdPoolLabel`, since the selector would have no key.

Give a cluster its own image repository rather than a tag on the shared one, so a build driven
there is never what everything else pulls, and deploy at an immutable ref:

```sh
make push PUSH_IMAGE=<registry>/viff:<sha> IMAGE_ARCH=amd64
make deploy PROFILE=eks                              # the profile's ref
make deploy PROFILE=eks IMAGE=<registry>/viff:<sha> # a particular build
```

Nothing here creates the class or the pool. On a cluster that has no `gp3` class,
`-e emitStorageClass=true` emits a `viff-gp3` class (`WaitForFirstConsumer` → the
pod is auto-affinitized to the volume's AZ), which needs the [EBS CSI driver addon] with
node-role IAM to create/attach volumes — otherwise the PVC stays `Pending`.

[EBS CSI driver addon]: https://docs.aws.amazon.com/eks/latest/userguide/ebs-csi.html

### The runners' state volume (`runnerStateSize`)

Each deployed runner mounts `/state`, which holds its **mirrors** — one bare mirror per
repository, shared by the tasks — and, where the `pkg` system is configured, its **cellar**. The
manifests carry an `emptyDir`, and `runnerStateSize: ""` leaves it that way. That is the default
and it is the wrong one for anything long-lived: the mirrors hold work, not just a cache. A
delivery that could not reach its remote leaves the commit under `refs/pending/<task>` for the
runner to retry, and a refused one under `refs/held/...` for somebody to look at, and on an
`emptyDir` all of it dies with the pod — along with the clone-costs-no-network property the
mirrors exist for.

A size emits one PVC per deployed runner (`viff-runner-state`, `codex-runner-state`,
`claude-runner-state`), and `runnerStateClassName` names the class (`""` omits the field and takes
the cluster default). `ReadWriteOnce` is right because each runner's `strategy` is `Recreate`:
one writer, since two pods writing one mirror is a fetch racing a fetch.

> ⚠️ **`fsGroup` is why this cannot be a one-line volume swap.** A freshly provisioned volume
> mounts root-owned `0755`, and the runners run `runAsNonRoot: true`, `runAsUser: 65532` with
> every capability dropped — so without it the runner cannot create its mirrors directory and
> dies at its first fetch. docd needs none of this because docd runs as **root**, and the
> `emptyDir` hides it because the kubelet gives that `0777`. The PVC patch therefore emits
> `fsGroup: 65532` with `fsGroupChangePolicy: OnRootMismatch` (so the kubelet checks the top
> directory instead of chowning a whole cellar on every start). These pods also set
> `hostUsers: false`, which makes this fsGroup *through a user namespace* — worth confirming on
> the first roll, with a root initContainer that chowns `/state` as the fallback:
> ```sh
> kubectl -n viff exec deploy/viff-runner -- sh -c 'ls -ld /state && touch /state/.w && rm /state/.w'
> ```

Unlike docd's, these are **standalone PVCs and not a `volumeClaimTemplate`**, so the orphan-delete
warning above does not apply: on a class that allows expansion, growing one is an edit and the
Deployment is never touched.

```sh
kubectl -n viff patch pvc viff-runner-state -p '{"spec":{"resources":{"requests":{"storage":"20Gi"}}}}'
```

**Size it over the cellar's own ceiling.** `pkg.collect-above` in a runner's config is an LRU
high-water mark — evict least recently used past this, and absent, half the volume. A threshold larger than
the volume can never fire, and a full disk collects instead. So `collect-above` sits under
`runnerStateSize`, with the mirrors taking the rest; the mirrors are usually the smaller half.

> ⚠️ **A claim and spot nodes are a bad pair, and this is what `runnerPool` is for.** A volume is
> pinned to one AZ, so a runner that holds one can only ever schedule in its own zone. Worse, a
> spot node reclaimed without a clean detach leaves the volume attached to an instance that no
> longer exists, and the replacement pod waits on the attachment timing out. `runnerPool` and
> `runnerPoolLabel` work exactly as `docdPool` does — the `nodeSelector` to go there and the
> matching toleration to be let in — and may name the pool docd is already on, since the knob is
> a value and not a nodegroup.

**The PVC does not cover a task's workspace.** `runnerd` makes its work directory under `TMPDIR`,
so a task's checkout, its `HOME` and its build caches are on the **container** filesystem, not on
`/state`. That is what `runnerEphemeralRequest` / `runnerEphemeralLimit` are for, and they matter
as much as the memory pair: with no request the kubelet ranks evictions by usage-over-request with
nothing to rank against, and can take the neighbours instead of the offender.

`runnerMemoryRequest` / `runnerMemoryLimit` bound the runner **and every task it is running**.
`runnerd` caps nothing — no limit on how many tasks it accepts, and no per-task cgroup, since a
task is a plain child process under bwrap — so an unbounded number of tasks sits inside a bounded
cgroup, contending with each other, and a runaway one is OOM-killed in the runner's own cgroup
rather than taking the node and its neighbours with it. That is what makes a runner affordable to
put beside the stateful tier. There is no CPU knob: a CPU limit on a runner throttles the builds
its tasks exist to run.

## A private registry (`imagePullSecret`)

A private image repository needs a pull credential, and the knob **names** a Secret that
already exists in the namespace; it does not create one — a checked-in manifest is not where a
registry credential belongs. Make it by hand (`kubectl -n viff create secret docker-registry
<name> …`), or have the External Secrets Operator fan it in: a `ClusterExternalSecret` that
targets every namespace puts the Secret there when the namespace is created, hourly-refreshed
and rotating on its own.

⚠️ **Do not copy the Secret between namespaces.** It carries `ownerReferences` to the
`ExternalSecret` in the namespace it came from, owner references are namespace-local, and the
garbage collector deletes a dependent whose owner it cannot find — so the copy disappears,
with an `OwnerRefInvalidNamespace` event as the only trace.

The knob attaches it to the namespace's **`default` ServiceAccount**, not to each pod spec:
the ServiceAccount admission plugin copies `imagePullSecrets` into every pod created in the
namespace, so viffd, docd and every iod are covered by one object rather than a
patch each. The build emits that ServiceAccount immediately after the Namespace, before the
workloads, because the copy happens **at pod creation** — an account that gains the secret
later does nothing for pods already standing:

```sh
kubectl -n viff rollout restart deploy/viffd statefulset/docd   # after attaching it late
```

## Reaching it: the tailnet (`tailscaleExpose`, off by default)

Two annotations the [Tailscale Kubernetes operator] watches for — it stands up its own proxy
pod per Service and dials that Service's ClusterIP, so nothing changes for in-cluster callers.
The operator has to already be installed; **nothing here notices if nobody is watching**, and
an unexposed Service looks exactly like an exposed one until you go looking on the tailnet.

| tailnet name | what | port |
|---|---|---|
| `viff` | the viffd API — `viff -addr http://viff:9797 …` | 9797 |
| `viff-docd` | docd's client face: the store, read/write, including scoped writes | 7071 |

The device names track `namespace`, so a second viff on the same tailnet is a second name
rather than the `-1` suffix the operator would otherwise pick. `-e tailscaleTags=tag:viff`
if the ACL wants its own tag instead of the operator's default `tag:k8s`.

`tailscaleExpose` adds no Services — it annotates the ones the deploy already has. A Service
gets one tailnet IP, so a face that an ACL should be able to grant separately has to be its
own Service. `docd-headless` is
deliberately not exposed: the operator refuses a headless Service outright, recording `headless
Services are not supported` as an `INVALIDSERVICE` warning event and exposing nothing — which
is the reason the plain name `docd` belongs to a face and the governing Service carries the
suffix.

**`/status` answers with the tailnet name too**, which is what lets a store client on a laptop
find docd. Such a client reads docd's address off `/status` and dials it from where *it* is, so
being told `docd:7071` — true inside the cluster, meaningless outside — would stop it. With
`tailscaleExpose`, viffd is given `-docd-advertise-addr viff-docd:7071`
([up.md](../docs/reference/up.md#when-a-client-cannot-reach-docd-where-viff-does)). It keeps
*dialling* `docd:7071` — routing the engine's own traffic through a proxy pod to reach a
container beside it would be absurd — and only the answer changes.

There is one published address, so this is a choice about which client matters, and it goes to
the one outside. A client running *inside* the namespace would now be handed a tailnet name; it
should be passed the Service name directly rather than discovering it.

[Tailscale Kubernetes operator]: https://tailscale.com/kb/1236/kubernetes-operator

| `imagePullSecret` | `""` | name an existing pull Secret, onto the `default` ServiceAccount |
| `storageClassName` | `""` | PVC class; `""` = cluster default (eks: `gp3`) |
| `storageSize` | `10Gi` | docd volume size |
| `emitStorageClass` | `false` | emit a `viff-gp3` StorageClass |
| `hostPV` | `false` | back the PVC with a static hostPath `PersistentVolume` (minikube) |
| `hostPath` | `/mnt/viff` | the PV's in-VM host path when `hostPV` |
| `docdPool` | `""` | put docd on the `<docdPoolLabel>=<x>` nodes, tolerating their taint |
| `docdPoolLabel` | `viff/pool` | the key the pool's nodes are labelled and tainted with |
| `spotViffd` | `false` | let viffd prefer `eks.amazonaws.com/capacityType: SPOT` |
| `docdMemoryRequest` / `docdMemoryLimit` | `""` | docd's memory. `""` on both is BestEffort — right on a laptop, wrong on a cluster: a catch-up is read into memory before it is emitted, so with no request the store is first in line when the kubelet needs memory back and free to take the node with it. A limit does not prevent the read, it decides who dies of it — the container, attributably, instead of the node |
| `docdGoMemLimit` | `""` | docd's `GOMEMLIMIT`, the soft Go heap ceiling. | `docdCompactionCutoff` | `""` | logd's compaction cutoff, emitted as a ConfigMap passed to `o sys up`. `""` is compaction **off**, which on a long-lived store keeps every root snapshot ever written — snapshots bound what a read replays, not what the volume holds. | `tailscaleExpose` | `false` | put the API and docd's two faces on the tailnet |
| `tailscaleTags` | `""` | `tailscale.com/tags` for both; `""` leaves the operator's `tag:k8s` |
| `secretStore` | `aws-secretsmanager` | the `ClusterSecretStore` every entry below comes from |
| `llmSecretKey` | `""` | entry for `viff-llm`; `""` emits no `ExternalSecret` |
| `gitSecretKey` / `slackSecretKey` / `linearSecretKey` / `githubSecretKey` / `runnerSecretKey` / `codexSecretKey` / `claudeSecretKey` / `issuerSecretKey` / `runnerStoreKey` | `""` | the same, one per credential |
| `llmModel` | `""` | `OPENAI_MODEL` for viffd; `""` leaves the driver's `gpt-4o` |
| `systemCharter` | `""` | a charter, by path (relative to `deploy/`, or absolute), mounted into viffd and installed at start as the system (`VIFF_SYSTEM_CHARTER`); read at start, so a change takes a restart. | `authConfig` | `""` | viff's `auth` block, a file by path (relative to `deploy/`, or absolute), mounted into viffd as its config (`VIFF_CONFIG`): who verifies people, which iods are trusted for whose accounts, how the iods prove themselves ([Who a request is from](#who-a-request-is-from-authconfig-iodtokens-runnertokens)). eks: `auth/eks.tony` |
| `iodTokens` | `false` | give the slack, github and git iods a ServiceAccount each and a projected token, so each proves it is the iod (eks and minikube: on) |

| `issuer` | `http://viff:9797` | the name viffd's tokens are issued under, the auth file's `auth.issuer.url`: what each runner holds viffd's tokens to (`VIFF_ISSUER`). The runners read the keys at viffd's in-cluster url, so this is a name |
| `issuerDiscoveryOpen` | `false` | let anyone reaching the API server read its OpenID discovery and keys, which viffd needs where the cluster itself is the iods' issuer (minikube: on; EKS needs none) |
| `runner` | `false` | deploy the viff runner (its own image; install it with `viff runner add`) |
| `runnerImage` | `signadot/viff-runner:latest` | its image ref — a tag in another repository is fine |
| `runnerConfig` | `""` | its configuration, a file by path as `authConfig` is, in place of the manifest's ([The viff runner](#the-viff-runner-runner-off-by-default)) |
| `codexRunner` | `false` | deploy the codex runner beside it: the viff runner in an image with Codex in it, offering the codex agent |
| `codexRunnerImage` | `signadot/viff-runner:codex` | its image ref |
| `codexRunnerConfig` | `""` | as `runnerConfig`, for the codex runner |
| `claudeRunner` | `false` | deploy the claude runner beside them: the viff runner in an image with Claude Code in it, offering the claude agent |
| `claudeRunnerImage` | `signadot/viff-runner:claude` | its image ref |
| `claudeRunnerConfig` | `""` | as `runnerConfig`, for the claude runner |
| `runnerStateSize` | `""` | a PVC per deployed runner for `/state` (the mirrors and the pkg cellar); `""` keeps the manifests' `emptyDir`, where both die with the pod ([The runners' state volume](#the-runners-state-volume-runnerstatesize)) |
| `runnerStateClassName` | `""` | the class those PVCs ask for; `""` omits the field and takes the cluster default. Deliberately not `storageClassName`, which doubles as the `hostPV` switch |
| `runnerPool` | `""` | put the runners on the `<runnerPoolLabel>=<x>` nodes, tolerating their taint, as `docdPool` does — and may name the same pool. On-demand matters once `/state` is a claim |
| `runnerPoolLabel` | `viff/pool` | the key that pool's nodes are labelled and tainted with |
| `runnerMemoryRequest` / `runnerMemoryLimit` | `""` | the runners' memory; a limit bounds the runner **and** its tasks, which share its cgroup |
| `runnerEphemeralRequest` / `runnerEphemeralLimit` | `""` | the runners' `ephemeral-storage`: a task's workspace and build caches are on the container filesystem, not on the state volume |

## Iods (optional)

The seam to an external system — reflecting it in, and acting out
([docs/io.md](../docs/io.md)). Five are shipped, each its own Deployment + Service, each **off
by default** and turned on independently — the git ones cost a clone, the SaaS ones cost a
credential in the cluster.

```sh
make deploy E='-e gitIod=true'
o build deploy -O yaml -e slackIod=true -e linearIod=true | kubectl apply -f -
```

They run `iod`, the connector binary in the same image
([docs/reference/iod.md](../docs/reference/iod.md) is its surface). Deploying one does
**not** install it: an install carries an ownership claim viff proves against what is already
standing, so it stays a verb somebody runs.

```sh
viff iod add git       http://git-iod:9801   -root git
viff iod add slack http://slack-iod:9801 -root slack
viff iod add linear    http://linear-iod:9801 -root linear
viff iod
```

Run from wherever your `viff` reaches the API — no `kubectl exec` needed, and none wanted: it
would depend on your current kubectx and skip the version-skew check the CLI's own transport
does on every request. **The url stays the in-cluster Service name**, because it is *viffd*
that dials it: the CLI only posts `{name, root, url}`, and the probe happens server-side
(`internal/viffd/io.go`). The mirror image of `-docd-advertise-addr`, where the client dials and
so the address has to be reachable from where the client is.

⚠️ **The name has to match `<x>IOName`.** The hint url is baked into the pod
(`http://viff:9797/iods/<name>/hint`), so a registration under a different name means
viff 404s every delivery — loud, but only if you look.

⚠️ **Widening what an iod reflects is two steps, and the deploy is only the first.** A
registration stores the ownership claim as it stood when it was installed, so adding a
repository to `gitMirror`, `gitIssueMirror` or `githubRepos` and rolling the pod leaves viff
holding the old claim — and it FENCES the new slice out rather than letting the iod write
outside what was proved. The symptom is an iod that looks healthy and reflects nothing new.
Re-run the same `viff iod add` afterwards; it updates the claim in place.

```sh
viff iod show git-issue    # `owns` is what viff holds
viff iod check git-issue   # `says` is what the iod claims now
viff iod add git-issue http://git-issue-iod:9801 -root git-issue   # reconcile them
```

Driven, on an iod moved from one repository to two: only the first repository's entities were
written while the claim was stale, `check` showed the two values side by side, and the second
repository's appeared within a pass of the re-add. Removal is the other direction and needs no
such care — but note it asks for `-forget` or `-keep`, and there is nothing to forget on a
iod you are only widening.

### Credentials

The three that need one (Slack, Linear, GitHub) take it from a Secret, and `optional` is **false** on purpose: a Slack
iod with no token has nothing to reflect, so it fails to start rather than installing clean
and failing every pass. Either name a store entry — `slackSecretKey`, `linearSecretKey`,
`githubSecretKey`, see [Credentials](#credentials) — or create the Secret yourself:

```sh
kubectl -n viff create secret generic viff-slack \
  --from-literal=SLACK_BOT_TOKEN=xoxb-… \
  --from-literal=SLACK_SIGNING_SECRET=…

kubectl -n viff create secret generic viff-linear \
  --from-literal=LINEAR_API_KEY=lin_api_… \
  --from-literal=LINEAR_WEBHOOK_SECRET=…
```

### Webhooks

viff dials an iod, and the iod dials viff — only the *delivery* leg comes from the
internet, and only the three SaaS iods have one (`slackWebhookHost`, `linearWebhookHost`,
`githubWebhookHost`). Set a host and an Ingress is emitted for it;
leave it empty and there is none, and the iod converges on the periodic resync (one minute)
instead of on delivery.

```sh
o build deploy -O yaml -e slackIod=true -e slackWebhookHost=slack.viff.example.com \
               -e ingressClassName=nginx | kubectl apply -f -
```

Then point Slack's Event Subscriptions request url at `https://<host>/slack/events`, and
Linear's Settings → API → Webhooks at `https://<host>/linear/webhook`. Each iod verifies its
own signature; viff never sees the delivery.

### A private mirror needs a credential

The git connector mounts a `viff-git` Secret at `/git-credentials`, `optional: true`, and
points git's credential helper at it. No Secret means an empty mount, a helper that answers
nothing, and an anonymous clone — which is what a public *mirror* wants, and is exactly what a
private one gets 404s from. `gitSecretKey` names the store entry, or create it yourself:

```sh
kubectl -n viff create secret generic viff-git \
  --from-literal=credential=$'username=x-access-token\npassword=<PAT>\n'
```

The token is in a Secret rather than in the `-mirror` url because the url is in the pod spec,
and a pod spec is not a secret. The helper is read-only on purpose: `credential.helper=store`
writes the file back on success *and* on failure, so against a read-only mount it spends a
1000ms lock timeout and prints a fatal-looking line on every clone and every fetch.

⚠️ **A private mirror needs that Secret before the connector starts** — without it the pod
crash-loops, with git's own "could not read Username" in the log.

### The git iod has no repositories

A pod has none, so `-mirror` makes one: it clones the remote at startup and fetches on every
pass. That is the read. The pod also runs the git iod's out half (`-out`): a tag or a branch
asked for under `git.<repo>.out` is pushed to the remote with the same credential, so the
`viff-git` credential must be allowed to push ([the out half of
git](../docs/reference/iod.md#the-out-half-of-git)); nothing is pushed that nobody asked for.
And it reflects the tree sha of each repository's `.viff/charters` directory on every ref
(`-tree .viff/charters`), which is what the repo-charters reconciler keys approval on, and
installs that tree into the viff when the reconciler asks (`{to: install.<address>}`), as
itself: the deployment's repopulate script holds `repos` out to it with `child-owner`. The mirror
lives on an `emptyDir`, so a restart re-clones; swap in a PVC if that gets expensive. For a
repository that already exists somewhere, run the same binary next to it with `-repo`, or skip
the deployment entirely and use `viff iod add -dir`.

### Carrying what people wrote across a wipe

A wipe takes the store with it: the store *is* the configuration, and there is no seed file a
fresh viff reads. So a deployment keeps a repopulate script of its own, run after the wipe and
after the tiers are up at the new vintage, that puts back what its files describe, in an order
the install checks impose. The runner first (`viff runner add`, with the pod's subject), since a
charter whose spawn no registered runner takes is refused at install. Then the iods (`viff iod
add`, each with its out place and who may ask through it), removing again one that could not be
reached so the next is not refused for overlap, and the two grants the rest depend on:
`mirror.runners` held to the admin with everyone reading, and `repos` with `child-owner` for the
git iod. Then the deployment's charters (`viff charter -a`), each as one step, after the iods
because a package that sends through an outbox (deploy-announce) is refused until the iod it
names is registered; and one that latches on its own outbox is seeded before it is installed,
since installing it first announces every tag there has ever been (the example's header says
how). What is gone and nothing reconstructs: open gates, in-flight flows and the firing history.

What people wrote by hand in places no charter manages is carried by `carry.sh`, over a list
somebody keeps of those places, a file the deployment keeps beside its profile:

```sh
deploy/carry.sh capture <addr> <places file> ~/carry   # before the wipe, as an admin
# … wipe, ship, repopulate …
deploy/carry.sh restore <addr> <places file> ~/carry   # after, as each place's owner
```

Each place crosses with its owner, its grants and its data, and not its history. A charter
package's address, or anything beneath one, is refused: a charter is installed again from its
file and its state derived again. So is a place with somebody else's place beneath it. The
directory holds people's data; keep it out of the repository.

### Repo charters

The reconciler of the viff repository's charters is a charter viff ships at the system level
(`internal/repocharters`, [the example](../docs/reference/examples/repo-charters/repo-charters.tony)):
what runs in viff is the tree of `.viff/charters` that `viff/live` holds, and `viff/live` holds
only a tree an answer said yes to. `viff/live` is a record the git iod keeps, `refs/viff/live`,
not a branch: each entry holds the charters tree and names the commit of main it came from
([a record](../docs/reference/iod.md#a-record)). A change to the charters that reaches main is put
to the team on an issue, with two commit statuses on main's commit: `viff/check`, what viff's
charter check says an install would do, and `viff`, the decision. A yes adds it to
`viff/live`, and a commit to main that leaves the charters alone installs nothing.
While the charters on main would be refused, one issue says so and why; it closes when main
passes the check. A refused install has an issue of its own, closed by the next install that
succeeds. Each reopens for the next round rather than multiplying. The pieces on a deployment:

- **`repoCharters`** in viffd's config file (`deploy/auth/eks.tony`, mounted by the
  `authConfig` knob) names the repository, its GitHub name, the branch its charters follow
  (`main` unless the entry says `branch`), the address its charters install at and who may
  answer; viffd renders and installs the reconciler as the system at start, after
  the iods are restored ([up](../docs/reference/up.md)).
- **Registrations held to the admin, readable by all.** The deployment's repopulate script
  replaces the rows under
  `mirror.runners` so that `user:admin@viff` alone creates beneath it, and everyone reads the
  node and what is registered: writing a registration vouches for a runner ([who the runner
  is](../docs/runners.md#who-the-runner-is)), and on this deployment that is the admin's act.
  The seed's own row, `owner` beneath `mirror.runners` to everyone, is the open viff's and
  stands on a deployment that skips this.
- **The git iod** with `-tree .viff/charters -out` (on), registered with its out place
  (the deployment's repopulate script), and `child-owner` under `repos` for `agent:git-iod`, so
  it installs the charters as itself. With `gitAsApp` it pushes as the App, so `refs/viff/live`
  is written as the App.
- **The github iod** with `githubOut` on, registered with its out place, and the App allowed
  `statuses: write` for the commit status ([the GitHub App](#the-github-app)).

Pausing the repository's charters is `viff flow suspend -charter repos.viff -r -why …`. The
reconciler is the system's, and no request may suspend it. Turning it off is dropping the
repository's entry from `repoCharters` and restarting viffd: the reconciler goes, with its state
under `repo-charters.<repo>`, and the charters it installed at `at` go on running
([up](../docs/reference/up.md)).

`gitIssueIod` reflects the issues `git issue` keeps inside a repository — a mirror clone maps
every ref (`+refs/*:refs/*`), so `refs/git-issues/*` is already there and this needs no credential
and no route the git connector does not already have. It is a second pod rather than a flag on
the first because the two answer different questions about one directory and write disjoint
slices (`git.*`, `git-issue.*`): run one, the other, or both. Register it like the git one,
under any name you like — it is polled and posts no hints, so nothing has to match:

```sh
viff iod add git-issue http://git-issue-iod:9801 -root git-issue
```

It mirrors whatever `gitMirror` names, until you say otherwise with `gitIssueMirror`. Say
otherwise as soon as the two sets differ: `git issue` is a habit some repositories have and
others do not, so a `gitMirror` that has grown a second repository will otherwise have this pod
cloning one it can reflect nothing from.

| knob | default | meaning |
|---|---|---|
| `gitIod` | `false` | deploy the git connector |
| `gitMirror` | the viff repo | `[<id>=]<url>` to mirror; comma-separated for several |
| `gitIssueIod` | `false` | deploy the git-issue connector |
| `gitIssueMirror` | `""` | its own mirror set, when it differs; `""` follows `gitMirror` |
| `gitAsApp` | `false` | the git and git-issue iods fetch, and the git iod pushes, as the GitHub App, its keys read from `viff-github`, in place of the `viff-git` PAT |
| `githubOut` | `false` | the github iod acts back as the App: comments, pull requests, merges, reviews, closes, checks and issues asked for under `github.<org>.<name>.out` |
| `slackIod` | `false` | deploy the Slack connector (needs the `viff-slack` Secret) |
| `slackIodName` | `slack` | the registration name — must match `viff iod add <name> -root slack` |
| `slackWorkspace` | `""` | the id prefix; `""` takes the team name from the token |
| `slackWebhookHost` | `""` | Ingress host for `/slack/events`; `""` emits none |
| `linearIod` | `false` | deploy the Linear connector (needs the `viff-linear` Secret) |
| `linearIodName` | `linear` | the registration name |
| `linearTeams` | `""` | comma-separated team keys; `""` is every team the credential sees. Quote it: `-e 'linearTeams="ENG,OPS"'` |
| `linearWebhookHost` | `""` | Ingress host for `/linear/webhook` |
| `ingressClassName` | `""` | class for both Ingresses; `""` leaves the cluster default |

## Who a request is from (`authConfig`, `iodTokens`, `runnerTokens`)

Without `authConfig`, a request to viffd is whoever its header says, as it has always been on a
tailnet nobody else reaches. With it, viffd verifies people and its own iods
([who a request is from](../docs/reference/perms.md#who-a-request-is-from)):

- **`authConfig`** mounts the named file as viffd's config (`VIFF_CONFIG`). The eks profile's,
  `deploy/auth/eks.tony`, names the slack and github iods as trusted for their own systems'
  accounts and the git iod for GitHub's, and the cluster as the issuer of the iods' tokens. It
  names no issuer for people: a person is who their CLI says (`mode: optional`), and binds their
  Slack or GitHub account by saying the nonce `viff account -link <provider>` gives them to the
  app ([accounts in other systems](../docs/reference/perms.md#accounts-in-other-systems)). An
  issuer for people, and `required`, come with the team's identity provider.
- **`iodTokens`** gives the slack, github and git iods a ServiceAccount each (`deploy/iod-tokens`)
  and a projected token with the audience `viff` at `/var/run/viff/token`, which `iod` reads as
  `VIFF_TOKEN_FILE` and sends with every request. The token's subject is
  `system:serviceaccount:<namespace>:<iod>`, which the auth config's `auth.iod.accounts` maps to
  the iod's principal and its installed name. The issuer is the cluster's own: `kubectl --context
  <ctx> get --raw /.well-known/openid-configuration` prints it, and on EKS it is `aws eks
  describe-cluster --query cluster.identity.oidc.issuer`. Where the issuer is the API server
  itself (minikube, kubeadm), the auth file also names the cluster's CA (`auth.iod.ca`, the
  bundle every pod has mounted) and `issuerDiscoveryOpen` lets viffd read the discovery
  document, which such a cluster otherwise grants to service accounts alone.
  `deploy/auth/minikube.tony` and the minikube profile are the worked example.
- **`runnerTokens`** does the same for the runners (`deploy/runner-tokens`), and gives viffd
  the other half: the two prove themselves to each other at the describe ([who the runner
  is](../docs/runners.md#who-the-runner-is)). A runner's token has the audience `viff`: it
  answers it on the describe to the viff it verified and presents it at viffd's door, and
  `viff runner add -subject system:serviceaccount:viff:<runner>` holds the registration to
  it, as a deployment's repopulate script does. Viffd's token toward a runner is one it signs
  itself, as the issuer the auth file's `auth.issuer` makes it, with the `viff-issuer` Secret
  this patch mounts (`issuerSecretKey`, or a Secret made by hand on minikube): minted for that
  runner's subject alone, so a copy taken at one runner opens no other's door. The patch names
  the viff in each runner's environment, `VIFF_URL`, where it reaches viffd and reads its
  keys, and `VIFF_ISSUER` from the `issuer` knob, the name the tokens are issued under; the
  audience a runner takes is its own token's subject, so nothing is typed per runner. The
  description stays public. Each runner announces itself at start, in a loop until viffd knows
  it, and viffd describes it then and there. A pod's readiness (`GET /ready`) is its server and
  nothing else, so the ship and the registrations may come in either order: `viff runner add
  <name> <url> -identity <name> -subject system:serviceaccount:viff:<name>` for each runner
  after the runners' tier ships is answered by the new pod's handshake, and before it (`--no-probe`,
  since the old pods cannot answer) is caught up by the new pod's hello within its backoff. A
  runner pod with no token answers none, and the add is refused rather than the first spawn.

Each ServiceAccount here carries the pull secret the way `default` does: the `imagePullSecret`
patch covers every ServiceAccount this deploy emits.

## Credentials

Every credential this deploy needs is a Secret it **names** and does not carry. Each has a
knob naming the secret-store entry it comes from, and each emits an `ExternalSecret`
(`deploy/secrets/`) that materialises it, refreshed hourly. Leave the knob empty and no
`ExternalSecret` is emitted at all — then the Secret is yours to create by hand, which is the
right answer on a cluster with no External Secrets Operator.

A Secret made by hand stands in a knob's way: the `ExternalSecret` owns the Secret it makes
(`creationPolicy: Owner`) and does not take over one it did not. So moving a credential from a
Secret made by hand to a knob is three steps, in this order: create the entry, delete the
Secret, deploy with the knob set. Deployed with the old Secret still there, the
`ExternalSecret` sits in `SecretSyncedError` while the pods keep the old value and look
healthy; a pod that starts after the Secret is gone and before the next sync comes up without
it.

One knob per credential rather than one for all, because they are held by different processes
and revoked on different days: the git iod's PAT and the runner's push token can be the
same secret and should still be two entries, so taking one away does not take the other.

⚠️ **The entry's own key names land in the Secret verbatim** (`dataFrom.extract` copies them
through), so an entry that spells them differently syncs green and configures nothing. These
are the names each consumer reads:

| knob | Secret | keys the entry must have | read as |
|---|---|---|---|
| `llmSecretKey` | `viff-llm` | `PORTKEY_API_KEY`, `PORTKEY_VIRTUAL_KEY` (`PORTKEY_BASE_URL`, `OPENAI_MODEL` optional) | env, by viffd **and** the viff runner, which without `PORTKEY_API_KEY` starts with the viff agent closed, offering scripts alone, and says so |
| `gitSecretKey` | `viff-git` | `credential` — the value being `username=x-access-token\npassword=<PAT>\n` | a **file** at `/git-credentials/credential` |
| `slackSecretKey` | `viff-slack` | `SLACK_BOT_TOKEN`, `SLACK_SIGNING_SECRET` | env; **not** optional — no token, no start. `SLACK_BOT_TOKEN` also in the runners, `optional: true` in the pod spec, and as the **file** `slack-bot` in [their secret store](#the-runners-secret-store): a runner without it starts with `slack` closed, and says so |
| `linearSecretKey` | `viff-linear` | `LINEAR_API_KEY` (the `Authorization` header verbatim), `LINEAR_WEBHOOK_SECRET` | env; `LINEAR_API_KEY` also in the runners, `optional: true` in the pod spec, and as the **file** `linear` in their secret store: a runner without it starts with `linear-issue` closed, and says so |
| `githubSecretKey` | `viff-github` | `GITHUB_TOKEN`, or `GITHUB_APP_ID`, `GITHUB_APP_INSTALLATION_ID` and `GITHUB_APP_PRIVATE_KEY` ([The GitHub App](#the-github-app)); and `GITHUB_WEBHOOK_SECRET` | env; **not** optional — no Secret, no start |
| `runnerSecretKey` | `viff-runner` | `gitToken` | env (`GITHUB_TOKEN`), in the runners and never in the sandbox |
| `codexSecretKey` | `viff-codex` | `OPENAI_API_KEY` | env, in the codex runner, `optional: true` — a runner without it starts, and its first codex spawn fails; written as each task's Codex login |
| `claudeSecretKey` | `viff-claude` | `ANTHROPIC_API_KEY` | env, in the claude runner, `optional: true` — a runner without it starts, and its first claude spawn fails, not logged in; handed to each task's claude process |
| `issuerSecretKey` | `viff-issuer` | `issuer.pem`, an RSA private key in PEM (`openssl genrsa 2048`) | a **file** at `/etc/viff/issuer/issuer.pem`, read by viffd alone: what it signs its own tokens with, the gate credential and the token toward each runner |
| `runnerStoreKey` | `viff-runner-secrets` | any: each key is a secret's name in [the runners' secret store](#the-runners-secret-store) — lower case letters, digits, `-`, `_`, `.`, not starting with `.` | a **file** at `/secrets/<key>` in each runner, `optional: true`: what a runner performs a system with that no other Secret holds |

### Creating the entries

An entry is a JSON object whose keys are the ones in the table. Write it to a file rather than
an argument, so no value reaches your shell history, and remove the file at the end. The region
has to be the one the `ClusterSecretStore` reads; an entry in another region
or another account is invisible to the cluster no matter what the knob says. The names below
are a convention, `<deployment>/viff/<name>`; the knob is what ties a name to its Secret.

```sh
put() { aws secretsmanager create-secret --region <region> --name "$1" --secret-string file://"$2"; }

printf '{"PORTKEY_API_KEY":"%s","PORTKEY_VIRTUAL_KEY":"%s"}' "$pk" "$vk" > /tmp/e.json
put <deployment>/viff/llm /tmp/e.json

# `credential` is a FILE git's helper cats, so its value carries real newlines — a \n inside a
# JSON string is one, and the trailing one matters to git.
printf '{"credential":"username=x-access-token\\npassword=%s\\n"}' "$pat" > /tmp/e.json
put <deployment>/viff/git /tmp/e.json

# The same PAT, held by a different process and revocable on its own.
printf '{"gitToken":"%s"}' "$pat" > /tmp/e.json
put <deployment>/viff/viff-runner /tmp/e.json

printf '{"SLACK_BOT_TOKEN":"%s","SLACK_SIGNING_SECRET":"%s"}' "$bot" "$sig" > /tmp/e.json
put <deployment>/viff/slack /tmp/e.json

printf '{"LINEAR_API_KEY":"%s","LINEAR_WEBHOOK_SECRET":"%s"}' "$key" "$sig" > /tmp/e.json
put <deployment>/viff/linear /tmp/e.json

printf '{"GITHUB_TOKEN":"%s","GITHUB_WEBHOOK_SECRET":"%s"}' "$tok" "$sig" > /tmp/e.json
put <deployment>/viff/github /tmp/e.json

printf '{"OPENAI_API_KEY":"%s"}' "$key" > /tmp/e.json
put <deployment>/viff/codex /tmp/e.json

printf '{"ANTHROPIC_API_KEY":"%s"}' "$key" > /tmp/e.json
put <deployment>/viff/claude /tmp/e.json

# The runners' secret store: each key a file at /secrets/<key>, named as the store names them.
# Only for what no other Secret holds; the Slack and Linear tokens reach the store on their own.
printf '{"some-server":"%s"}' "$token" > /tmp/e.json
put <deployment>/viff/runner-secrets /tmp/e.json

# `issuer.pem` is a FILE viffd reads, a multi-line PEM: jq carries its newlines into the JSON
# string, and nobody but viffd ever sees the private half.
openssl genrsa -out /tmp/issuer.pem 2048
jq -n --rawfile pem /tmp/issuer.pem '{"issuer.pem": $pem}' > /tmp/e.json
put <deployment>/viff/issuer /tmp/e.json

rm -f /tmp/e.json /tmp/issuer.pem
```

Rotating one later is `put-secret-value --secret-id <name>` instead of `create-secret`; ESO
picks it up on the next refresh, and the pods that already read it need a rollout.

**Check the key names landed**, which is the failure nothing else catches — this prints names
only, never values:

```sh
kubectl -n viff get secret viff-git -o go-template='{{range $k,$v := .data}}{{$k}}{{"\n"}}{{end}}'
```

**The GitHub token needs `Contents` as well**, which is the permission easiest to leave off
and the first one used. Read-only on **Contents, Metadata, Issues, Pull requests and Actions**
(plus Discussions with `githubDiscussions`). Without Contents the connector's first read is a
`403 Resource not accessible by personal access token` on `git/ref/heads/<branch>` — it reads
the default branch's ref before anything else. Get the set wrong and you edit the token's
permissions in place (Settings → Developer settings → Fine-grained tokens → the token → Edit): the
token does not change, so the secret needs no update. A new token — regenerated, or minted to
replace one — does need the entry updated, and that is `put-secret-value`, not `create-secret`,
since the name already exists:

```sh
printf '{"GITHUB_TOKEN":"%s"}' "$tok" > /tmp/e.json
aws secretsmanager put-secret-value --region <region> \
  --secret-id <deployment>/viff/github --secret-string file:///tmp/e.json && rm /tmp/e.json
kubectl -n viff annotate externalsecret viff-github force-sync=$(date +%s) --overwrite
kubectl -n viff rollout restart deploy/github-iod
```

The last two lines are why a rotation is three commands and not one: `refreshInterval` is an
hour, so the `force-sync` annotation is what makes ESO look now, and `envFrom` is read at pod
start, so the connector needs restarting to see the new value even once the Secret has it.

**Create the entry before setting the knob.** A knob naming an entry that does not exist is an
`ExternalSecret` stuck in `SecretSyncedError` and a Secret that never appears — which for the
Slack iod is a pod that will not start, and for the git iod is an empty credential
mount, an anonymous clone, and a private repository answering 404.

**`envFrom` and secret volumes are read when the pod starts**, so a Secret that lands after its
consumer needs `kubectl -n viff rollout restart deploy/<x>`. The `secrets/` dir renders ahead
of the workloads so a first apply does not need that.

### The GitHub App

The github iod's out half acts as an app rather than as a person's token: as `<your-app>[bot]`,
it can review pull requests that people open, and people can review the ones it opens. A
person's token can do neither, since GitHub refuses a review from a pull request's own author.
The app's webhook stays off: the iod's events come from repository webhooks
([Webhooks](#webhooks)).

**`iod github` authenticates as the app when its entry carries the app.** That is three keys:
`GITHUB_APP_ID`, `GITHUB_APP_INSTALLATION_ID`, and `GITHUB_APP_PRIVATE_KEY`, the PEM. Given with
`GITHUB_TOKEN`, the app is used and the token is ignored. So the keys can be added to the entry
before a build that reads them is deployed, and the token is removed once one runs. A build that
predates app support ignores the three keys. To add them to the entry, keeping what it holds:

```sh
(umask 077
 aws secretsmanager get-secret-value --region <region> --secret-id <deployment>/viff/github \
   --query SecretString --output text \
 | jq --arg id <app id> --arg inst <installation id> \
      --rawfile key <path to the app's private key>.pem \
      '. + {GITHUB_APP_ID: $id, GITHUB_APP_INSTALLATION_ID: $inst, GITHUB_APP_PRIVATE_KEY: $key}' \
   > /tmp/e.json)
aws secretsmanager put-secret-value --region <region> \
  --secret-id <deployment>/viff/github --secret-string file:///tmp/e.json && rm /tmp/e.json
kubectl -n viff annotate externalsecret viff-github force-sync=$(date +%s) --overwrite
kubectl -n viff rollout restart deploy/github-iod
```

The iod's log says `authenticating as app <app id>, installation <installation id>` when it
starts. Once it does, `GITHUB_TOKEN` can be removed from the entry the same way, with
`del(.GITHUB_TOKEN)` as the jq program.

**A repository the iod reflects must be in the installation.** Add it under the app's installation
settings (the org → Settings → GitHub Apps → the app → Configure → Repository access).

Create the app from a manifest, through GitHub's
[manifest flow](https://docs.github.com/en/apps/sharing-github-apps/registering-a-github-app-from-a-manifest):
`redirect_url` is a one-off local server that exchanges GitHub's code for the app's credentials,
and `hook_attributes.url` is a placeholder, since the webhook is inactive:

```json
{
  "name": "<your-app>",
  "url": "https://github.com/<org>/<repo>",
  "description": "viff's github iod: reflects repositories into viff and acts back on them (comments, pull requests, merges, reviews, closes).",
  "public": false,
  "hook_attributes": {"url": "https://example.invalid/github/webhook", "active": false},
  "redirect_url": "http://127.0.0.1:8765/done",
  "default_permissions": {
    "metadata": "read",
    "actions": "read",
    "contents": "write",
    "issues": "write",
    "pull_requests": "write"
  },
  "default_events": []
}
```

These permissions are the token's ([above](#creating-the-entries)) plus the out half's writes:
Issues and Pull requests to comment, open, review and close, and Contents to merge. **Commit
statuses (`statuses: write`) is not in the manifest and is wanted**: the repo-charters reconciler
puts its `viff` and `viff/check` statuses on the head of a pull request to main that changes the
charters, and on main's commit for a change that reached main unanswered (an input's
`commitStatus`), and
without the permission GitHub refuses the status and the refusal lands on the input's status.
Add it under the App's settings (Permissions & events → Repository permissions → Commit
statuses: Read and write); the installation then asks an org owner to approve the new
permission. Two are left off on purpose:

- **Discussions.** Discussions stay off unless `githubDiscussions` is turned on.
- **Workflows.** Without it, GitHub refuses the app a merge of a pull request that changes
  `.github/workflows/*`, and the refusal lands on the input's status.

Changing the app's permissions makes the org owner approve the installation again.

### The model credential (`llmSecretKey`)

viffd does `envFrom` a `viff-llm` Secret (`optional: true`), so it deploys and runs on the
credential-free `scripted` driver without it. For `llm`-driver agents, either make one:

```sh
kubectl -n viff create secret generic viff-llm \
  --from-literal=PORTKEY_API_KEY=... \
  --from-literal=PORTKEY_VIRTUAL_KEY=... \
  --from-literal=OPENAI_MODEL=gpt-4o          # optional; the driver defaults to gpt-4o
```

or have a profile name the entry:

```
llmSecretKey: "<deployment>/viff/llm"
llmModel: "claude-sonnet-5"     # what that credential routes to; "" = the driver's gpt-4o
```

A console is where a key is **issued**; a secret store is how it reaches a cluster that cannot
log into that console. So a Portkey key belongs in both.

Two values, not three: viff sends `x-portkey-api-key` and `x-portkey-virtual-key` to Portkey's
gateway and nothing else. **The provider key the virtual key resolves to — an Anthropic key,
say — stays in Portkey.** viff never sees it and has nowhere to put it.

That indirection is also why `llmModel` exists. A virtual key resolves to one provider, so the
model has to be one *that* provider serves: an Anthropic-backed key asked for the driver's
`gpt-4o` default fails on every call, and nothing about the credential can warn you. It is set
as an explicit env var, which also means it wins over an `OPENAI_MODEL` in the Secret — model
choice is deployment config and belongs in the open, not smuggled into a store entry.
`viff status` is the check: it reports `llm.available` and a masked key.
- **`envFrom` is read when the pod starts.** A Secret that lands after viffd does nothing
  until it restarts — `kubectl -n viff rollout restart deploy/viffd`.

## The viff runner (`runner`, off by default)

A place code work **runs** — its own `Deployment` + `Service` + `ConfigMap`, a workspace and a
process per task, bubblewrap around the process. It is `runnerd`
([reference/runnerd.md](../docs/reference/runnerd.md)) with the configuration its ConfigMap
holds, offering the viff agent and scripts, each under its own ceilings; what a task works on is
its spawn's. It needs `runnerTokens`, on by default: a runner does not start without the viff it
serves and its token to prove itself with. So the `viff-issuer` Secret is required
(`issuerSecretKey`, or `kubectl -n viff create secret generic viff-issuer
--from-file=issuer.pem=<(openssl genrsa 2048)`), and the auth file names `auth.issuer` with it. Not an iod and not the engine: viff reaches it by url, and deploying it does not
install it.

```sh
make runner-push IMAGE_ARCH=amd64 RUNNER_IMAGE=<registry>/viff-runner:<tag>
make deploy PROFILE=eks E='-e runner=true -e runnerImage=<registry>/viff-runner:<tag>'
viff runner add viff-runner http://viff-runner:9802 -identity viff-runner \
  -subject system:serviceaccount:viff:viff-runner    # it acts as runner:viff-runner, and proves it is the pod
```

**Its ceilings are placeholders.** The configuration each runner's manifest carries names
`github.com/example/` repositories, a Linear team `TEAM` and a Slack channel `viff`, so a task
on it reaches none of a deployment's own until the deployment says which. It says so with a file
of its own, carried in whole in place of the manifest's: `runnerConfig` for this runner,
`codexRunnerConfig` and `claudeRunnerConfig` for the other two. Copy the manifest's
`viff-runner.tony`, name your repositories, team and channels, and point the knob at it.

Viff routes the charters' scripts and viff-agent spawns to it, as the runner that offers them
(viffd itself hosts nothing: `localRunner: false`). The url is the Service. The subject is its pod's ServiceAccount (`runnerTokens`): the add is the
handshake, and a pod that answers no token, or another's, is refused there.

That last line is the install, and it probes — so `reach: "a runner"` is the deployment's own
acceptance test, and the first thing that exercises bubblewrap on the node. As with an iod,
the url is the in-cluster Service name because viffd dials it (`client.Probe`, server-side);
your CLI needs to reach the *API*, not the runner.

**Its own image, not necessarily its own repository.** The two images are sized by different
things (the runtime image is thin and pinned to the engine; this one carries the toolchain the
repositories it serves must build), which is a reason for two *builds*, not two registry
repositories. A tag in the existing one is a repository you do not have to create and a pull
credential you do not have to re-grant. It needs no `imagePullSecrets` of its own either way:
it runs as the namespace's `default` ServiceAccount like everything else here.

⚠️ **One thing it shares with viffd has to agree, and nothing checks that it does.** The
`ConfigMap`'s `agents.viff.settings.model.default` must be a model the `viff-llm` credential's
provider serves — the same value as `llmModel`. It fails at the first spawn rather than at deploy.

**The codex runner** (`codex-runner`) is the same runner in an image with Codex pinned in it
(`deploy/codex-runner`), offering the codex agent and no scripts (its config has no `script:`). Its key is the `viff-codex` Secret, from
the store entry `codexSecretKey` names ([Credentials](#credentials)), or made by hand where the
knob is empty (`kubectl -n viff create secret generic viff-codex
--from-literal=OPENAI_API_KEY=<key>`); it pushes with the same token. Install it as `viff runner add codex http://codex-runner:9802
--identity codex-runner --subject system:serviceaccount:viff:codex-runner`; viff routes a spawn
for `agent: {name: codex}` to it.

**The claude runner** (`claude-runner`) is the same runner in an image with Claude Code pinned
in it (`deploy/claude-runner`), offering the claude agent and no scripts. Its credential is the `viff-claude`
Secret, from the store entry `claudeSecretKey` names ([Credentials](#credentials)), or made by
hand where the knob is empty (`kubectl -n viff create secret generic viff-claude
--from-literal=ANTHROPIC_API_KEY=<key>`): an API key of the Console workspace the work is
billed to. It pushes with the same token the viff runner does. Install it as `viff runner add claude
http://claude-runner:9802 --identity claude-runner --subject system:serviceaccount:viff:claude-runner`;
viff routes a spawn for `agent: {name: claude}` to it.

⚠️ **It needs three things from the pod spec, and each was found by a spawn refusing itself.**
`hostUsers: false`, `procMount: Unmasked`, `seccompProfile: Unconfined` — in that order of
dependency, because the API will not accept the second without the first.

| symptom | actual cause |
|---|---|
| `bwrap: No permissions to create new namespace, likely because the kernel does not allow non-privileged user namespaces` | the kernel does allow them; a seccomp filter blocks the `clone` |
| `bwrap: Can't mount proc on /newroot/proc: Operation not permitted` | `/proc` has masked submounts, so it is not *fully visible*, and an unprivileged userns may not mount a fresh procfs |

Both messages name the wrong layer, which is worth knowing before you go reading sysctls.

**`seccompProfile: Unconfined`.** Bottlerocket's kubelet
applies `RuntimeDefault` to every pod naming no profile, and containerd's default profile masks
the namespace flags out of `clone` unless the caller holds `CAP_SYS_ADMIN` — which this pod
drops. bwrap then reports *"the kernel does not allow non-privileged user namespaces"*, which
sends you to a sysctl that is fine (`user.max_user_namespaces` was `15000` on the node where
this was found). The kernel allows it; the seccomp filter does not. Check with
`grep ^Seccomp /proc/self/status` in the pod — `2` means a filter is loaded.

**`procMount: Unmasked`.** With the filter lifted, bwrap got one step further and failed to
mount `/proc`. `--unshare-pid` and `--proc /proc` were already in its argv, so the PID namespace
was not it: the runtime masks eleven paths under `/proc` (`bus`, `fs`, `irq`, `sys`,
`sysrq-trigger` read-only; `acpi`, `interrupts`, `kcore`, `keys`, `latency_stats`, `timer_list`
covered), and since Linux 4.x an unprivileged user namespace may only mount a fresh procfs when
it can already see a **fully visible** one. `grep " /proc" /proc/self/mountinfo` in the pod
shows them.

**`hostUsers: false`.** Required — `procMount: Unmasked` is refused without it — and it is also
what makes the other two affordable. The trade is real and worth stating: this pod gives up the
runtime's blanket syscall filter and its `/proc` masking so the *task* can be given namespace
containment. That is the right way round here (the runner binary is ours, the agent is not), and
without it the runner refuses every spawn, so the strictly safer pod is one that runs nothing.
The pod's own user namespace is what keeps that from being a straight loss: unfiltered syscalls
against an unmasked `/proc` from inside a userns are not the exposure they are in the host's.

A `Localhost` seccomp profile (RuntimeDefault plus the clone flags) is tighter and costs a
profile file on every node. Pod Security Admission set to `baseline` or `restricted` would
reject both `Unconfined` and `Unmasked`; the `viff` namespace carries no PSA labels.

`/state` is an `emptyDir`, and the manifest says why that is the first thing to change: a
delivery that could not reach its remote leaves the commit under `refs/pending/<task>/<repo>`
for the runner to retry, and on an `emptyDir` that work dies with the pod.

### The runners' secret store

Each runner mounts a projected volume at `/secrets`, its [secret
store](../docs/reference/runnerd.md#the-secret-store): one file to a secret, read by the runner
at each act and by no task — no sandbox binds the directory, and the runner refuses to start with
a store where one would. The volume's sources are all `optional`, so it is there on every
deployment and empty on one with none of them:

| file | from | the system that may name it |
|---|---|---|
| `slack-bot` | `viff-slack`'s `SLACK_BOT_TOKEN` | `slack` |
| `linear` | `viff-linear`'s `LINEAR_API_KEY` | `linear-issue` |
| `<key>` | each key of `viff-runner-secrets` (`runnerStoreKey`) | what comes to need one and has no Secret of its own |

The manifests' configuration names no secret, so each system reads its variable as it always
has, from the same Secrets. A deployment moves a system to the store in its runner configuration
(`runnerConfig` and the other two): `secrets: {dir: /secrets, systems: {slack: slack-bot,
linear-issue: linear}}`. The variable is then not read, and the runner says so at start if it is
set; a rotation is the next act's, with no restart, where a variable takes a rollout; and a
named secret whose file is absent or empty at start closes its system to every doer, with a
warning that names the file and the directory. The iods go on reading the same Secrets, so a
token is kept once.

Not a `subPath` mount, on purpose: one does not follow a Secret that changes. The projected
volume follows one within the kubelet's sync period, as the `ExternalSecret` follows the entry
within its `refreshInterval`.

## Shipping one tier at a time

A plain `make deploy` applies **everything** in one `kubectl apply`. That is the right thing
when nothing about the wire between the tiers has changed, and the wrong thing when it has:
viffd and docd speak logd's session protocol, so a protocol change (v0.0.173's match shape,
say) means the two vintages must not meet — a client of one against a server of the other has
its path read as `""`, which is the **root**: an answer, with a commit, not an error. One apply
starts both rolling and there is no point in it where you can say which is up.

`SELECT=tier=<tier>` applies one tier out of the render, and `WAIT=1` makes the target block
until what it applied is rolled out, so a protocol-changing ship is a sequence somebody can
read, the images pushed first at an immutable ref:

```bash
CTX=<the profile's kubeContext>
REF=<registry>/viff:<sha>
RUNNERS="-e runnerImage=<registry>/viff-runner:<sha> -e codexRunnerImage=<registry>/viff-runner:codex-<sha> -e claudeRunnerImage=<registry>/viff-runner:claude-<sha>"

kubectl --context $CTX -n viff scale deploy/viffd --replicas=0
kubectl --context $CTX -n viff wait --for=delete pod -l app=viff,tier=viffd --timeout=2m

make deploy PROFILE=<profile> IMAGE=$REF E="$RUNNERS" SELECT=tier=docd WAIT=1      # the store; viffd is down, so nothing is talking to it
make deploy PROFILE=<profile> IMAGE=$REF E="$RUNNERS" SELECT=tier=viffd WAIT=1    # the engine, against a docd that is already up and new
make deploy PROFILE=<profile> IMAGE=$REF E="$RUNNERS" SELECT=tier=iods WAIT=1      # the iods
make deploy PROFILE=<profile> IMAGE=$REF E="$RUNNERS" SELECT=tier=runners WAIT=1   # the viff, codex and claude runners, their own images
```

The viffd step restores `replicas: 1` from the manifest, so the scale to 0 costs no
availability that a deploy was not already spending — viffd is `replicas: 1` with
`strategy: Recreate` and goes fully down on any apply. A deployment usually wraps these four in
a Makefile of its own, each target pushing the image its tier runs before applying (`make push`,
`make runner-push` and the codex and claude ones, at the commit's ref), so any one of them alone
is a whole ship; pushing a tag that is already there is a manifest check, not an upload.

The tier is the `tier` label every object in `deploy/` carries — `docd`, `viffd`, `iods`,
`runners` — and `kubectl apply -l` is what selects on it; the `runner` label beside it names which
runner (`-l runner=codex`, `-l runner=claude`). Objects with no tier (the Namespace,
the ServiceAccount, the ExternalSecrets) belong to none and are applied by a full `make
deploy`: a tier apply updates a deployment that exists rather than standing one up.

## When something stops answering (the admin face)

Every daemon here — viffd, each `iod`, the runners — serves `net/http/pprof`, full goroutine
stacks, and a short index of what it is and where it listens, on a port **one up from the one
it serves on**: viffd's API is 9797, its admin face 9798; an iod's 9801/9802; the runners'
9802/9803.

```
kubectl -n viff port-forward deploy/viffd 9798 &
curl localhost:9798/                                   # what this process is, and its addresses
curl localhost:9798/debug/pprof/goroutine?debug=2      # where every goroutine is blocked
```

It is worth a port because it holds **nothing a request handler holds** — its own accept loop,
its own mux, no store call — so it answers exactly when the API face cannot. The half hour
viffd spent at 0/1 with every read timing out was a question about goroutines that nothing in
the pod could be asked; this is that answer. `-admin-addr` moves it, `off`
disables it, and the address is on `viff status` under `listen.admin`.
