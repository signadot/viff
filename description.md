# repo-charters: a pull request's charter check is made once per tree, so a verse that changes its mind never re-checks it

Seen at the ship of #24 (2026-10-19). The reconciler derives a pull request's check input as `{to: check.repos.verse, tree, sha}` (the `main`/`pull` rules of system/repocharters/charter.tony.tmpl), and the git iod skips a check whose status already holds a verdict for the same tree at the same `round` (io/gitcheck.go, `check`), the sha not compared. So the verdict stands for as long as the tree does: the old versed refused #24's tree ("field doer: expected string, got Object") at 18:48, the new versed came up at 21:27 and re-derived the candidate, the input's bytes did not change, and `verse/check` stayed red with the old refusal. Only the livecheck of `verse/live` carries a `round` (the reconciler's minute tick), so only it is made again.

A pull request's check should be made again when what it is checked against changes: at least once per versed start, which is the case here, and arguably on the same tick the livecheck uses while the verdict is `refused`, since a refusal is the verdict a new versed can reverse. The input needs a `round` for that; what names a versed start as a value a rule can read is the open question (nothing written at start carries the instant today). Until then the hand repair is to remove the stale `repo-charters.<repo>.check.<tree>~status`, which the next pass answers afresh.
