# verse task run: no way to give a run the tracker's facts (`with.git-issue`), so an ad-hoc task has no git-issue tools

Staging test drive, 2026-10-20. A task launched with `verse task run --runner verse-runner --git git.tony --policy issue.tony 'file an issue …'` had rows providing every `git-issue` verb, and no `git-issue-*` tool: the verse runner builds the tracker tools from `with.git-issue` (`issueTools(cl, ws, l.Doer.With.GitIssue, …)`), and `task run` has `--git` for the `git` facts and nothing for the tracker's. The policy installed, since the offer holds `git-issue` and the rows were within it, so nothing said the task would have no tool for what its rows allowed. The model then spent 48 boundaries looking for a `git issue` binary, trying to `go install` one, and reading `/proc` for the runner's processes.

Two things. `task run` takes the tracker's facts (`--git-issue <file>`, a list of `{repo}` as the spawn's `with.git-issue` is, or the same file as `--git` with the repositories that have a tracker), so an ad-hoc run can do what a charter's spawn can. And a launch whose rows name a system's verbs while its facts give the system nothing to act on is worth a word at admission ("rows name git-issue, and the launch names no tracker"), since a policy that provides a verb no tool backs is exactly a row that could never do anything.
