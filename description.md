## The spine

**1. System documents.** A schema (schemagen) for a system document — `setup` fields, `verbs` with their params and which are patterns, the resource grammar — and the four documents: `git`, `git-issue`, `github`, `linear`, versioned by date, shipped with verse as data (as the system charters are) and readable in the store at `verse.tools.systems.<name>@<date>`. A `System` registry in `runner/runnerd/delivery` that the existing tools are grouped under, with tool names derived `<system>-<verb>` and checked against the documents at runner start (a runner whose code lags a document fails to start, naming the verb). Done when: the eleven issue tools and ask/push/fetch/pr are listed from systems, the documents are in the store, and `verse-call-tool` lists the same names.

**2. Policy on the spawn, evaluated in the loop.** `policy:` on the spawn spec beside `gates:`: an ordered list of `{match: {system, verb, <params…>}, then: deny|ask|allow}` with a trailing default; `ask` may carry what a gate's ask carries (within, need). The supervisor evaluates it for system tool calls before any gate: first match wins; `deny` refuses with the rule's name in the note, `ask` poses the question as a gate does, `allow` proceeds. Offered tools derive from the policy when one is present (a verb with a reachable allow/ask is offered); `tools:` keeps working without one. Today's `gates:` keep working beside it; a spawn with both gets the stricter answer. Done when: a program under a policy is denied, asked and allowed as the list says, the brief and the binary list only what the policy reaches, and the read plane names the rule.

**3. Facts under `with.<system>`.** `with.git` (repo, from) and `with.git-issue` (repo) on the spawn, read where `repos:` is read today; `repos:` continues as an alias until the flip. Linear and github have no facts. Done when: a spawn written with `with.git` checks out and delivers as one written with `repos:` does, and the examples doc shows the new spelling.

**4. Runner ceilings and containment at admit.** The runner's config declares, per system, a ceiling policy (`allow`/`deny`, never `ask`) with the credential beside it: which forges and hosts, which branch patterns, which Linear teams. Describe publishes it. Admit checks the spawn's policy against it: every `allow`/`ask` within some runner `allow`, field by field (literal in pattern, pattern in pattern, glob containment), and within no earlier `deny`; a refusal names the rule and the ceiling line it falls outside. This replaces deriving capability from a hostname (the forge() finding on #22) and the `tools:` floor check in `offeredFor` for system tools. Done when: a spawn asking to propose on a host the runner's ceiling does not allow is refused at launch with both lines named, the Enterprise Server case is one `allow` in config, and the floor tests pass in the new form.

**5. Record.** Each system call's event carries system, verb and the matched params; a question names the rule; `GET /runner` lists the ceilings. Docs: the concepts paragraph "every external system has two faces" (iod and tools), the per-system page shape (what the iod reflects, what a charter writes, what a task can do, where the credential lives) with `git-issue` as the first page, and the examples doc's tools paragraphs rewritten around systems and policy.

## Then Slack

**6. The `slack` system.** Verbs `post` (channel), `reply` (channel, thread), `read` (channel or thread, since) and `react`; the runner performs them with its own bot token, reusing io/slack's API client; every write carries a footer naming the task (the attribution the iod can tie back to); `read` derives `network`. System document, ceiling (channels the token may post to), tests with a fake Slack API, and the `slack` per-system page. Explicitly not a bot, not a conversation surface, and not the way a task asks a person: `ask` stays that. Done when: a program posts a status to an allowed channel under an asking policy, is denied a channel outside it at admit, and reads a thread back.
