# runner workspace: a checkout gets the mirror's objects but none of its tags

A task's checkout shares the mirror's objects but gets none of its tag refs. The mirror itself fetches both: its `origin` remote has `+refs/heads/*:refs/heads/*` and `+refs/tags/*:refs/tags/*` (runner/runnerd/workspace/workspace.go:194). The checkout then gets a `mirror` remote with only `+refs/heads/*:refs/remotes/mirror/*` (workspace.go:430), and `syncMirrorRefs` (workspace.go:507) copies a ref only if `IsBranch()`. `linkObjects` hard-links the mirror's packs in, so every annotated tag object is in the checkout's store with nothing pointing at it. `Refresh` goes through the same `syncMirrorRefs`, so a later fetch does not bring them either.

Seen on staging, 2026-10-29, by the release-notes draft (verse-workshop examples/release-notes) against example/app: `refs/tags/` empty, `git describe --tags` failing with "No names found", and `git fsck --unreachable` listing ~339 dangling tag objects. The agent rebuilt `refs/tags/<name>` from each tag object's own name and target with `git update-ref`, which works for annotated tags and cannot recover lightweight ones. The review charter in the same example relies on `git describe --tags` for every release and would fail the same way on its first one.

The comment above the checkout's remote says the refs a clone would have made are copied by hand, every head of the mirror as `refs/remotes/mirror/<name>`. Tags are the other half of what a clone makes. Shape of the fix: add `+refs/tags/*:refs/tags/*` to the checkout's `mirror` remote, and have `syncMirrorRefs` set `refs/tags/<name>` for each of the mirror's tags alongside the branches, under the same rule that a ref the mirror no longer has is left in place. `git describe`, `git tag -l` and `git log <tag>..` then work in a checkout as they do in a clone, for lightweight tags too.
